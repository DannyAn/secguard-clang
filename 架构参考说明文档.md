# SecGuard-Lite 架构参考说明文档

> 本文档供 Python 语言实现的 sgre 项目参考，用于能力增强。文档包含：sgre.db 完整 Schema、基于场景的表用途说明（尤其是 Skill 如何使用各张表）、多级过滤机制详解与举例、以及端到端流水线说明。

---

## 1. 端到端流水线总览

```
Source Code (*.c)
    │
    ├─ ① Indexer (tree-sitter)          → Layer 1: files, functions, variables, expressions, types, locations
    ├─ ② Graph Builder                  → Layer 2: graph_nodes, graph_edges (CALL, DATA_FLOW, ALIAS, ...)
    ├─ ③ Security Event Detectors (17个) → Layer 3: security_events (原始候选事件, ~600条)
    ├─ ④ Candidate Planner (4级收敛)     → 收敛后证据包 (≤30条/漏洞类型)
    │   ├─ Seed: 从 security_events 按 event_type 取种子
    │   ├─ Filter Chain: 按漏洞类型配置的过滤器链
    │   ├─ Dedup: file:line:func:var 去重
    │   └─ Rank + Cap: 质量评分排序, 截断至 MaxCandidates(30)
    ├─ ⑤ Report Writer                  → sarif.sarif, report.md, <vuln-type>/NNN_<file>_<line>.md
    ├─ ⑥ Latest Symlink                 → scans/latest → scans/<scan_id>
    └─ ⑦ Console Summary                 → stderr 输出汇总表

AI Agent (security-auditor):
    ⑧ 读取收敛后证据包 → 加载 SKILL.md 分类规则 → 分类(confirmed/suspected/false-positive)
    ⑨ secguard_report --write           → Layer 4: findings (AI分类结果)
    ⑩ secguard_report --audit           → audit-report.md (per-skill 统计)
```

**核心设计理念：解决候选爆炸问题。** 17个检测器产生约600条原始 `security_events`，通过4级收敛管线缩减到约10条高质量证据包，AI Agent 只看到收敛后的证据，永远看不到原始候选。

## 2. sgre.db 完整 Schema

### 2.1 数据库配置

```sql
PRAGMA foreign_keys = ON;
PRAGMA journal_mode = WAL;
PRAGMA synchronous = NORMAL;
```

- 连接 DSN: `file:<path>?_pragma=foreign_keys(1)&_pragma=journal_mode(WAL)&_pragma=synchronous(NORMAL)`
- `MaxOpenConns(1)` (单连接，避免 SQLite 锁竞争)
- 新建 DB 文件权限 `0600`

### 2.2 四层分层模型

| 层 | 稳定性 | 表 | 用途 |
|----|--------|-----|------|
| Layer 1 — 程序事实 | 最稳定 | `files`, `functions`, `variables`, `expressions`, `types`, `locations` | 源码索引事实，与漏洞无关 |
| Layer 2 — 语义图 | 中等稳定 | `graph_nodes`, `graph_edges` | 调用图、数据流、可达性、CFG |
| Layer 3 — 安全证据 | 每轮扫描重置 | `security_events` | 检测器产生的原始事件（**瞬态工作表**） |
| Layer 4 — 发现结果 | 最易变 | `findings` | AI Agent 分类后的最终结果 |

辅助表：`scan_stats`（每轮扫描每类型的管线指标）、`function_summary`（函数返回值可空性摘要）

### 2.3 Layer 1 — 程序事实

#### `files` — 源文件索引

```sql
CREATE TABLE files (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    path       TEXT NOT NULL UNIQUE,
    language   TEXT DEFAULT 'c',
    checksum   TEXT,          -- SHA256, 用于增量索引
    loc        INTEGER,       -- 行数
    created_at INTEGER
);
CREATE INDEX idx_files_path ON files(path);
CREATE INDEX idx_files_checksum ON files(checksum);
```

**场景：** Indexer 遍历 `*.c`/`*.h` 文件，计算 SHA256 checksum。如果 checksum 未变，跳过重新解析。`path` 是绝对路径。

#### `functions` — 函数定义

```sql
CREATE TABLE functions (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    file_id     INTEGER NOT NULL REFERENCES files(id) ON DELETE CASCADE,
    name        TEXT,
    signature   TEXT,
    return_type TEXT,
    is_static   BOOLEAN,
    start_line  INTEGER,
    end_line    INTEGER
);
CREATE INDEX idx_functions_file_id ON functions(file_id);
CREATE INDEX idx_functions_name ON functions(name);
```

**场景：** Indexer 解析 AST 中的 `function_definition` 节点。`is_static` 用于判断函数是否仅文件内可见（影响可达性分析）。`start_line`/`end_line` 用于在 Graph Builder 中限定函数体内的调用表达式搜索范围。

#### `variables` — 变量声明

```sql
CREATE TABLE variables (
    id              INTEGER PRIMARY KEY AUTOINCREMENT,
    function_id     INTEGER REFERENCES functions(id) ON DELETE CASCADE,
    name            TEXT,
    type            TEXT,
    storage_class   TEXT DEFAULT 'auto' CHECK (storage_class IN ('auto','static','register','heap')),
    declaration_line INTEGER,
    is_pointer      BOOLEAN,
    is_nullable     BOOLEAN,
    source_kind     TEXT       -- 来源: malloc/external/param 等
);
CREATE INDEX idx_variables_function_id ON variables(function_id);
CREATE INDEX idx_variables_is_pointer ON variables(is_pointer);
CREATE INDEX idx_variables_storage_class ON variables(storage_class);
```

**场景：** Data Flow Builder 在 `detectPointerDeclarations` 中写入。`storage_class='heap'` 表示变量来自 malloc/calloc/realloc。`is_nullable=true` 表示可能为 NULL（堆分配或外部输入）。Null Source Detector 读取此表判断 NULL 值来源。

#### `expressions` — 表达式

```sql
CREATE TABLE expressions (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    function_id INTEGER REFERENCES functions(id) ON DELETE CASCADE,
    text        TEXT,
    line        INTEGER,
    expr_type   TEXT
);
CREATE INDEX idx_expressions_function_id ON expressions(function_id);
```

#### `types` — 类型定义

```sql
CREATE TABLE types (
    id   INTEGER PRIMARY KEY AUTOINCREMENT,
    name TEXT NOT NULL,
    kind TEXT        -- struct/union/enum/typedef/primitive
);
```

#### `locations` — 代码位置

```sql
CREATE TABLE locations (
    id      INTEGER PRIMARY KEY AUTOINCREMENT,
    file_id INTEGER NOT NULL REFERENCES files(id) ON DELETE CASCADE,
    line    INTEGER,
    column  INTEGER
);
CREATE INDEX idx_locations_file_id ON locations(file_id);
```

**场景：** `security_events` 通过 `location_id` 引用此表，Planner 在 seed 阶段通过 location 解析出 file:line 用于报告输出。

### 2.4 Layer 2 — 语义图

#### `graph_nodes` — 图节点

```sql
CREATE TABLE graph_nodes (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    entity_type TEXT NOT NULL,    -- 'function' | 'external_function' | 'variable_ref' | 'return_slot'
    entity_id   INTEGER NOT NULL, -- 对应 functions.id 或 variables.id
    properties  TEXT              -- JSON, 如 {"external":true}
);
CREATE INDEX idx_graph_nodes_entity ON graph_nodes(entity_type, entity_id);
```

#### `graph_edges` — 图边

```sql
CREATE TABLE graph_edges (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    src_id     INTEGER NOT NULL REFERENCES graph_nodes(id) ON DELETE CASCADE,
    dst_id     INTEGER NOT NULL REFERENCES graph_nodes(id) ON DELETE CASCADE,
    edge_type  TEXT NOT NULL CHECK (edge_type IN ('CALL','DATA_FLOW','OWNERSHIP_TRANSFER','RELEASE','BRANCH','ALIAS')),
    properties TEXT               -- JSON, 如 {"call_line":42}
);
CREATE INDEX idx_graph_edges_src ON graph_edges(src_id);
CREATE INDEX idx_graph_edges_dst ON graph_edges(dst_id);
CREATE INDEX idx_graph_edges_type ON graph_edges(edge_type);
CREATE INDEX idx_graph_edges_src_type ON graph_edges(src_id, edge_type);
CREATE INDEX idx_graph_edges_dst_type ON graph_edges(dst_id, edge_type);
```

**边类型说明：**

| edge_type | 含义 | 生产者 | 消费者 |
|-----------|------|--------|--------|
| `CALL` | 函数调用 | CallGraphBuilder | CallReachFilter (可达性) |
| `DATA_FLOW` | 数据流 | DataFlowBuilder | DataFlowFilter, 检测器 |
| `OWNERSHIP_TRANSFER` | 所有权转移 | (预留) | memory-leak 检测器 |
| `RELEASE` | 资源释放 | (预留) | resource-leak 检测器 |
| `BRANCH` | 分支 | (预留) | CFG 分析 |
| `ALIAS` | 别名 | UseAfterFree 检测器 | double-free 检测器 |

**可达性查询（递归 CTE）：**

```sql
WITH RECURSIVE reach(node) AS (
    SELECT :entry_node
    UNION
    SELECT ge.dst_id FROM graph_edges ge
    JOIN reach r ON ge.src_id = r.node
    WHERE ge.edge_type = :edge_type
)
SELECT node FROM reach;
```

**场景：** `CallReachFilter` 用此查询计算从 `main` 和所有非 static 函数出发的可达集合，丢弃不可达的候选。这是收敛管线中最关键的过滤步骤之一，通常能过滤掉 50%+ 的候选。

### 2.5 Layer 3 — 安全证据

#### `security_events` — 安全事件（**瞬态工作表**）

```sql
CREATE TABLE security_events (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    event_type  TEXT NOT NULL CHECK (event_type IN (
        'NULL_VALUE','DEREFERENCE','NULL_GUARD',
        'MEMORY_ALLOC','MEMORY_RELEASE',
        'RESOURCE_ACQUIRE','RESOURCE_RELEASE',
        'VARIABLE_DECLARE','VALUE_USE','VALUE_INIT',
        'BUFFER_ACCESS','INTEGER_OP','INJECTION',
        'USE_AFTER_FREE','DOUBLE_FREE','FORMAT_STRING',
        'INTEGER_OVERFLOW','RACE_CONDITION',
        'HARDCODED_SECRET','DEADLOCK','CRYPTO_MISUSE'
    )),
    entity_id   INTEGER,       -- 关联 functions.id 或 variables.id
    location_id INTEGER REFERENCES locations(id) ON DELETE SET NULL,
    properties  TEXT           -- JSON, 包含 variable, function, line, api_name 等
);
CREATE INDEX idx_security_events_type ON security_events(event_type);
CREATE INDEX idx_security_events_entity ON security_events(entity_id);
CREATE INDEX idx_security_events_location ON security_events(location_id);
CREATE INDEX idx_security_events_type_entity ON security_events(event_type, entity_id);
```

**关键设计：** 此表在每轮扫描开始时通过 `DELETE FROM security_events` 清空。它是检测器的**工作缓冲区**，不是用户可见的结果。AI Agent **禁止查询此表**（在 `secguard db` 命令中强制拦截）。

**`properties` JSON 示例：**

```json
// NULL_VALUE 事件
{"variable": "ptr", "function": "get_node", "source": "malloc", "line": 19}

// DEREFERENCE 事件
{"variable": "node", "function": "tc01_null_return", "line": 30, "deref_type": "member_access"}

// NULL_GUARD 事件
{"variable": "ptr", "scope_start": 15, "scope_end": 20, "condition": "NULL_CHECK", "strength": "strong"}

// MEMORY_ALLOC 事件
{"variable": "buf", "function": "alloc_buf", "api": "malloc", "size": "1024", "line": 10}
```

### 2.6 Layer 4 — 发现结果

#### `findings` — AI 分类后的发现

```sql
CREATE TABLE findings (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    rule_id       TEXT NOT NULL,           -- CWE-476, CWE-787 等
    severity      TEXT CHECK (severity IN ('critical','high','medium','low','info')),
    confidence    REAL CHECK (confidence >= 0.0 AND confidence <= 1.0),
    evidence      TEXT,                    -- JSON 证据片段
    status        TEXT DEFAULT 'open' CHECK (status IN ('open','confirmed','suspected','dismissed')),
    file_path     TEXT,
    line_number   INTEGER,
    function_name TEXT,
    properties    TEXT,                    -- JSON 附加属性
    scan_id       TEXT,                    -- 关联 scan_stats.scan_id
    created_at    INTEGER
);
CREATE INDEX idx_findings_rule_id ON findings(rule_id);
CREATE INDEX idx_findings_status ON findings(status);
CREATE INDEX idx_findings_severity ON findings(severity);
CREATE INDEX idx_findings_file ON findings(file_path);
CREATE INDEX idx_findings_scan_id ON findings(scan_id);
```

**CWE 白名单（15个）：** `CWE-476, CWE-787, CWE-401, CWE-78, CWE-89, CWE-404, CWE-457, CWE-416, CWE-415, CWE-134, CWE-190, CWE-362, CWE-798, CWE-667, CWE-327`。不在白名单中的 `rule_id` 会被 `InsertFinding` 拒绝。

**场景：** AI Agent 对每个收敛后候选进行分类后，通过 `secguard report --write` 写入此表。`scan_id` 关联到 `scan_stats`，用于在 `audit-report.md` 中统计每类型的 AI 分类准确率。

### 2.7 辅助表

#### `scan_stats` — 管线指标

```sql
CREATE TABLE scan_stats (
    id           INTEGER PRIMARY KEY AUTOINCREMENT,
    scan_id      TEXT NOT NULL,
    vuln_type    TEXT NOT NULL,
    seed_count   INTEGER NOT NULL,    -- 种子候选数
    final_count  INTEGER NOT NULL,    -- 收敛后候选数
    filter_chain TEXT,                -- JSON 过滤器链配置
    created_at   INTEGER
);
CREATE INDEX idx_scan_stats_scan_id ON scan_stats(scan_id);
CREATE INDEX idx_scan_stats_vuln_type ON scan_stats(vuln_type);
```

#### `function_summary` — 函数摘要（AI Agent 关键输入）

```sql
CREATE TABLE function_summary (
    function_id        INTEGER PRIMARY KEY REFERENCES functions(id) ON DELETE CASCADE,
    return_nullable    BOOLEAN,        -- 函数是否可能返回 NULL
    parameter_nullable TEXT,           -- JSON: 哪些参数可能为 NULL
    side_effect        TEXT,           -- 副作用描述
    summary_json       TEXT            -- 完整摘要 JSON
);
```

**场景：** UseAfterFree 和 DoubleFree 检测器在跨过程分析时读取此表，判断被调函数是否会释放参数或全局变量。`return_nullable` 也被 InterproceduralDetector 用于判断函数返回值是否需要 NULL 检查。

## 3. Skill 如何使用各张表（**最关键部分**）

### 3.1 Skill 架构说明

SecGuard-Lite 的 "Skill" 有两层含义：

1. **Go 侧 Skill（`internal/skills/`）**：`VulnTypeSkill` 封装 `planner.Plan()`，运行收敛管线，产出证据包。**Skill 不直接写 SQL 查询**，而是通过 `Store` 接口调用 CRUD 方法。

2. **Agent 侧 Skill（`extension/shared/skills/<type>/SKILL.md`）**：分类规则文档，告诉 AI Agent 如何对证据包中的候选进行 confirmed/suspected/false-positive 分类。**SKILL.md 不包含 SQL**，包含的是分类规则、安全函数列表、修复建议模板。

### 3.2 各 Skill（漏洞类型）使用的表

| 漏洞类型 | Seed 事件类型 | 读取的表 | 写入的表 | 关键过滤链 |
|----------|-------------|---------|---------|-----------|
| **null-deref** | `DEREFERENCE` | `security_events`, `functions`, `locations`, `graph_edges`(CALL), `graph_nodes` | (只读) | non_nullable → array_oob → nullable_source → call_reach → guard → safe_function → bounds_check |
| **buffer-overflow** | `BUFFER_ACCESS` | `security_events`, `functions`, `locations` | (只读) | call_reach → safe_function → bounds_check |
| **memory-leak** | `MEMORY_ALLOC` | `security_events`, `functions`, `locations`, `graph_edges`(CALL) | (只读) | call_reach → safe_function → has_release(MEMORY_RELEASE) |
| **injection** | `INJECTION` | `security_events`, `functions`, `locations` | (只读) | call_reach → safe_function → bounds_check |
| **resource-leak** | `RESOURCE_ACQUIRE` | `security_events`, `functions`, `locations`, `graph_edges`(CALL) | (只读) | call_reach → safe_function → has_release(RESOURCE_RELEASE) |
| **uninit** | `VALUE_USE` | `security_events`, `functions`, `locations` | (只读) | call_reach → safe_function → bounds_check |
| **use-after-free** | `USE_AFTER_FREE` | `security_events`, `functions`, `locations`, `function_summary`, `graph_edges`(CALL) | (只读) | call_reach → safe_function → lifetime(CFG) |
| **double-free** | `DOUBLE_FREE` | `security_events`, `functions`, `locations`, `function_summary` | (只读) | call_reach → safe_function → bounds_check |
| **format-string** | `FORMAT_STRING` | `security_events`, `functions`, `locations` | (只读) | call_reach → safe_function → bounds_check |
| **integer-overflow** | `INTEGER_OVERFLOW` | `security_events`, `functions`, `locations` | (只读) | call_reach → safe_function → bounds_check |
| **race-condition** | `RACE_CONDITION` | `security_events`, `functions`, `locations` | (只读) | call_reach → safe_function → bounds_check |
| **hardcoded-secret** | `HARDCODED_SECRET` | `security_events`, `functions`, `locations` | (只读) | call_reach → safe_function → bounds_check |
| **deadlock** | `DEADLOCK` | `security_events`, `functions`, `locations` | (只读) | call_reach → safe_function → bounds_check |
| **crypto-misuse** | `CRYPTO_MISUSE` | `security_events`, `functions`, `locations` | (只读) | call_reach → safe_function → bounds_check |

### 3.3 典型场景：null-deref Skill 完整流程

```
① Seed: 从 security_events WHERE event_type='DEREFERENCE' 取所有解引用事件
   → 每条事件通过 entity_id 关联 functions 表获取函数名
   → 通过 location_id 关联 locations 表获取 file:line
   → 从 properties JSON 提取 variable name

② Filter: non_nullable_array_suppress
   → 读取 variables 表 WHERE is_pointer=0 AND storage_class='auto'
   → 丢弃非指针数组变量的解引用候选

③ Filter: array_oob_precedence
   → 查询同 file:line 的 BUFFER_ACCESS 事件
   → 如果存在，丢弃 null-deref 候选（数组越界优先）

④ Filter: nullable_source
   → 查询函数是否有 NULL_VALUE 事件
   → 丢弃没有 NULL 值来源的候选

⑤ Filter: call_reach
   → 递归 CTE 查询 graph_edges WHERE edge_type='CALL'
   → 计算从 main 和非 static 函数的可达集合
   → 丢弃不可达的候选

⑥ Filter: guard
   → 查询 NULL_GUARD 事件
   → 如果解引用行在 guard 的 scope_start..scope_end 内，丢弃候选

⑦ Filter: safe_function_exclude
   → 检查函数名是否在安全包装器列表中 (SafeCopy_*, SafeQuery_* 等)
   → 丢弃安全函数中的候选

⑧ Filter: bounds_check
   → 查询 NULL_GUARD 事件 WHERE condition='NULL_CHECK' OR 'TRUTH_CHECK'
   → 强 guard 丢弃候选，弱 guard 保留但标记为 suspected

⑨ Dedup: 按 file_id:line:func_name:var_name 去重

⑩ Rank + Cap: 按 QualityScore 排序，截断至 30 条
```

### 3.4 典型场景：memory-leak Skill 完整流程

```
① Seed: 从 security_events WHERE event_type='MEMORY_ALLOC' 取所有分配事件

② Filter: call_reach → 丢弃不可达的分配

③ Filter: safe_function_exclude → 丢弃安全包装器中的分配

④ Filter: has_release
   → 查询同函数同变量的 MEMORY_RELEASE 事件
   → 如果存在释放事件，丢弃候选（已释放）
   → 注意：这是路径不敏感的，CFG 敏感的释放检查在检测器内部完成

⑤ Dedup + Rank + Cap
```

### 3.5 典型场景：use-after-free Skill 完整流程

```
① Seed: 从 security_events WHERE event_type='USE_AFTER_FREE' 取所有释放后使用事件
   → 检测器已在内部完成跨过程分析（通过 function_summary 表）

② Filter: call_reach → 丢弃不可达

③ Filter: safe_function_exclude

④ Filter: lifetime (CFG 敏感)
   → 重新解析函数 AST，构建 CFG (Scope 树)
   → 对每条候选，检查 free 行是否能到达 use 行
   → 如果 free 的 scope 有 early exit (return/break) 阻止到达 use，丢弃候选
   → 这是消除误报的关键过滤器

⑤ Dedup + Rank + Cap
```

### 3.6 Agent 侧 SKILL.md 使用方式

AI Agent 收到收敛后的证据包后，按以下流程使用 SKILL.md：

```
1. 对每个漏洞类型，加载对应的 SKILL.md
   例如：.claude/skills/null-deref/SKILL.md

2. SKILL.md 提供：
   - Evidence Pattern: 确认该漏洞需要哪些证据片段
   - Safe Patterns (P0 Exclusion): 哪些模式直接排除
   - Safe Wrappers (P1 Exemption): 哪些安全包装器排除
   - Classification Rules: confirmed/suspected/false-positive 判定规则
   - Common False Positives: 常见误报模式
   - Fix Suggestions: 修复代码模板
   - Severity Matrix: 严重度评定矩阵

3. Agent 对每条候选，按 SKILL.md 规则分类
   → confirmed: 证据完整，确认为真实漏洞
   → suspected: 证据部分，需要人工判断
   → false-positive: 安全函数/包装器/守卫消除风险

4. Agent 通过 secguard report --write 将分类结果写入 findings 表
```

## 4. 多级过滤机制详解与举例

### 4.1 过滤器接口

```go
type Filter interface {
    Name() string
    Apply(ctx context.Context, candidates []Candidate) ([]Candidate, error)
}
```

每个过滤器接收上一个过滤器的输出，返回过滤后的候选列表。过滤器链按配置顺序执行，如果某步输入为空则短路。

### 4.2 候选数据结构

```go
type Candidate struct {
    DerefEventID, FunctionID, LocationID, FileID int64
    FunctionName, VariableName string
    Line int
    HasNullableSource, IsReachable, HasDataFlow, IsGuarded, NonNullable bool
    GuardStrength, SuspicionLevel string   // "strong" | "weak", "confirmed" | "suspected" | "possible"
    QualityScore float64
}
```

### 4.3 所有过滤器详解

#### `non_nullable_array_suppress` — 非空数组抑制

**逻辑：** 丢弃 `NonNullable == true` 的候选（数组变量不会为 NULL，解引用不是 null-deref）。

**举例：**
```c
int arr[10];
arr[5] = 1;  // DEREFERENCE 事件产生，但 arr 不是指针，NonNullable=true → 丢弃
```

#### `array_oob_precedence` — 数组越界优先

**逻辑：** 如果同一 file:line 既有 `DEREFERENCE` 又有 `BUFFER_ACCESS` 事件，丢弃 `DEREFERENCE` 候选（按数组越界处理，不重复报 null-deref）。

**举例：**
```c
char *buf = malloc(10);
buf[15] = 'x';  // 同时产生 DEREFERENCE 和 BUFFER_ACCESS → 丢弃 DEREFERENCE，保留 BUFFER_ACCESS
```

#### `nullable_source` — 可空来源要求

**逻辑：** 只保留函数有 `NULL_VALUE` 事件的候选（函数中存在可能产生 NULL 的来源）。

**举例：**
```c
int *get_ptr() { return malloc(sizeof(int)); }  // 有 NULL_VALUE 事件 (malloc 可能失败)
int use() { int *p = get_ptr(); return *p; }    // 保留：有可空来源

int *get_static() { static int x; return &x; }  // 无 NULL_VALUE 事件
int use2() { int *p = get_static(); return *p; } // 丢弃：无可空来源
```

#### `call_reach` — 调用可达性

**逻辑：** 用递归 CTE 计算 `graph_edges` 中 `edge_type='CALL'` 的传递闭包，从 `main` 和所有非 static 函数出发。丢弃不可达函数中的候选。

**举例：**
```c
static void dead_code() { int *p = NULL; *p; }  // 不可达 → 丢弃
void reachable() { int *p = NULL; *p; }           // 可达 → 保留
int main() { reachable(); return 0; }             // main 调用 reachable
```

#### `guard` — NULL 守卫过滤

**逻辑：** 查询 `NULL_GUARD` 事件，如果解引用行在守卫的 `scope_start..scope_end` 范围内，且变量名匹配，丢弃候选。

**举例：**
```c
int *p = get_ptr();
if (p != NULL) {      // NULL_GUARD 事件: scope_start=3, scope_end=5, variable="p"
    *p;               // 在守卫范围内 → 丢弃
}
*p;                   // 在守卫范围外 → 保留
```

#### `safe_function_exclude` — 安全函数排除

**逻辑：** 检查函数名是否在安全包装器列表中，或变量名是否包含安全函数名。

**安全函数列表：** `memcpy_s, strcpy_s, sprintf_s, strcat_s, snprintf, strncpy, strlcpy, strlcat, execve, sqlite3_prepare_v2, sqlite3_bind_text, sqlite3_bind_int, sqlite3_bind_blob, mkstemp, openat`

**安全包装器列表：** `SafeCopy_copy, SafeCopy_strcpy, SafeQuery_prepare, SafeQuery_bind_text, SafeQuery_exec, ResourceHandle_create, ResourceHandle_destroy, LockGuard_create, LockGuard_release`

**举例：**
```c
SafeCopy_strcpy(dst, src, n);  // 在安全包装器中 → 丢弃
strcpy(dst, src);               // 不在安全列表中 → 保留
```

#### `bounds_check` — 边界检查过滤

**逻辑：** 查询 `NULL_GUARD` 事件中 `condition='NULL_CHECK'` 或 `'TRUTH_CHECK'` 的记录。强守卫丢弃候选，弱守卫保留但标记为 `suspected`。

**举例：**
```c
if (p) { *p; }           // 强守卫 (TRUTH_CHECK) → 丢弃
if (p != 0) { *p; }      // 强守卫 → 丢弃
if (p != NULL) { *p; }   // 强守卫 → 丢弃
if (some_flag && p) { *p; } // 弱守卫 → 保留但标记 suspected
```

#### `has_release` — 释放事件过滤

**逻辑：** 对 memory-leak，查询同函数同变量的 `MEMORY_RELEASE` 事件；对 resource-leak，查询 `RESOURCE_RELEASE` 事件。如果存在释放，丢弃候选。

**举例：**
```c
int *p = malloc(10);  // MEMORY_ALLOC 事件
// ... 使用 p ...
free(p);              // MEMORY_RELEASE 事件 → 丢弃 memory-leak 候选
```

#### `lifetime` — 生命周期过滤（CFG 敏感）

**逻辑：** 重新解析函数 AST，构建 CFG（Scope 树）。对 use-after-free 候选，检查 `free` 行是否能到达 `use` 行。如果 `free` 的 scope 有 early exit（return/break/continue）阻止到达 `use`，丢弃候选。

**举例：**
```c
void foo(int cond) {
    int *p = malloc(10);
    if (cond) {
        free(p);
        return;       // early exit: free 的 scope 无法到达 use
    }
    *p;               // use: 保留？不！lifetime 过滤器发现 free 后有 return
                      //       free 无法到达 use → 丢弃 use-after-free 候选
}
```

### 4.4 过滤器链配置

每种漏洞类型在 `registry.go` 中配置了不同的过滤器链：

| 漏洞类型 | 过滤器链 | 典型收敛率 |
|----------|---------|-----------|
| null-deref | non_nullable → array_oob → nullable_source → call_reach → guard → safe_function → bounds_check | ~95% (120→5) |
| memory-leak | call_reach → safe_function → has_release | ~90% |
| resource-leak | call_reach → safe_function → has_release | ~90% |
| use-after-free | call_reach → safe_function → lifetime | ~85% |
| 其他10种 | call_reach → safe_function → bounds_check | ~80% |

### 4.5 排序与截断

收敛后，候选按 `QualityScore` 降序排序：

```
QualityScore = severityValue(API) * 0.60 + confidenceValue(suspicion) * 25 + impactBonus * 0.15
```

- `severityValue`: critical API (system, popen) = 100, high API (strcpy, sprintf) = 80, medium API (strncpy, snprintf) = 60, other = 40, empty = 20
- `confidenceValue`: confirmed = 1.0, suspected = 0.7, possible = 0.5
- `impactBonus`: 20 if critical/high API, else 0

排序后截断至 `MaxCandidates`（默认 30）。

### 4.6 完整收敛举例

假设一个 C 项目有 100 个文件，17 个检测器产生 600 条 `security_events`：

```
原始事件: 600 条 security_events
    │
    ├─ null-deref (Seed: DEREFERENCE 事件 = 120 条)
    │   ├─ non_nullable: 120 → 80 (丢弃 40 条非指针数组)
    │   ├─ array_oob: 80 → 75 (丢弃 5 条与 BUFFER_ACCESS 重叠)
    │   ├─ nullable_source: 75 → 60 (丢弃 15 条无可空来源)
    │   ├─ call_reach: 60 → 45 (丢弃 15 条不可达)
    │   ├─ guard: 45 → 20 (丢弃 25 条有 NULL 守卫)
    │   ├─ safe_function: 20 → 18 (丢弃 2 条安全包装器)
    │   ├─ bounds_check: 18 → 8 (丢弃 7 条强守卫, 3 条弱守卫保留为 suspected)
    │   ├─ dedup: 8 → 7 (去重 1 条)
    │   └─ rank + cap: 7 → 7 (< 30, 无截断)
    │   → 最终: 7 条 null-deref 候选
    │
    ├─ memory-leak (Seed: MEMORY_ALLOC 事件 = 80 条)
    │   ├─ call_reach: 80 → 60
    │   ├─ safe_function: 60 → 58
    │   ├─ has_release: 58 → 12 (丢弃 46 条已释放)
    │   └─ rank + cap: 12 → 12
    │   → 最终: 12 条 memory-leak 候选
    │
    └─ ... 其他 12 种类型 ...

总计: ~600 → ~80 条收敛后候选 (跨 14 种类型)
AI Agent 只看到这 80 条，进行分类
```

## 5. 17 个检测器详解

| # | 检测器 | 产生的事件类型 | 核心逻辑 |
|---|--------|-------------|---------|
| 1 | `null_source` | NULL_VALUE | 检测返回 NULL、malloc 结果、外部调用赋值 |
| 2 | `dereference` | DEREFERENCE | 检测 `->`、`*ptr`、数组下标解引用 |
| 3 | `null_guard` | NULL_GUARD | 检测 `if (ptr != NULL)`、`if (!ptr)` 等守卫 |
| 4 | `interprocedural` | DEREFERENCE | 跨过程：未守卫参数解引用 + 可空参数传入 |
| 5 | `buffer_overflow` | BUFFER_ACCESS | 检测 memcpy/strcpy/sprintf/gets/scanf + 数组越界 |
| 6 | `memory_leak` | MEMORY_ALLOC, MEMORY_RELEASE | 路径敏感 CFG 分析，RAII 感知 |
| 7 | `injection` | INJECTION | 命令注入 (system/popen) + SQL 注入 (sprintf+sqlite3_exec) |
| 8 | `resource_leak` | RESOURCE_ACQUIRE, RESOURCE_RELEASE | fopen/open/socket/lock vs fclose/close/unlock |
| 9 | `uninit_variable` | VALUE_USE | 栈/堆未初始化，路径敏感 |
| 10 | `use_after_free` | USE_AFTER_FREE | free 后使用，跨过程通过 function_summary |
| 11 | `double_free` | DOUBLE_FREE | 同变量多次 free，跨过程 + 全局变量 |
| 12 | `format_string` | FORMAT_STRING | printf 族非字面量格式参数 |
| 13 | `integer_overflow` | INTEGER_OVERFLOW | size 类型算术流向 malloc/memcpy |
| 14 | `race_condition` | RACE_CONDITION | TOCTOU (access→fopen) + 共享状态竞态 |
| 15 | `hardcoded_secret` | HARDCODED_SECRET | 密码/密钥变量赋值字面量，高熵提示 |
| 16 | `deadlock` | DEADLOCK | 锁顺序反转，锁图环检测 |
| 17 | `crypto_misuse` | CRYPTO_MISUSE | 弱算法 (DES/MD5/SHA1/RC4)、弱 PRNG、短密钥 |

```python
class Store:
    """对应 Go 的 Store 接口，组合多个子接口"""

    # Layer 1: 程序事实
    def insert_file(self, path: str, checksum: str, loc: int) -> int: ...
    def get_file_by_path(self, path: str) -> Optional[File]: ...
    def insert_function(self, file_id: int, name: str, ...) -> int: ...

    # Layer 2: 语义图
    def insert_graph_node(self, entity_type: str, entity_id: int) -> int: ...
    def insert_graph_edge(self, src_id: int, dst_id: int, edge_type: str) -> None: ...
    def reachable_from_entry(self, entry_node: int, edge_type: str) -> Set[int]:
        """递归 CTE 查询可达集合"""
        cursor = self.conn.execute("""
            WITH RECURSIVE reach(node) AS (
                SELECT ?
                UNION
                SELECT ge.dst_id FROM graph_edges ge
                JOIN reach r ON ge.src_id = r.node
                WHERE ge.edge_type = ?
            )
            SELECT node FROM reach
        """, (entry_node, edge_type))
        return {row[0] for row in cursor}

    # Layer 3: 安全证据
    def insert_event(self, event_type: str, entity_id: int, properties: dict) -> None: ...
    def list_events_by_type(self, event_type: str) -> List[SecurityEvent]: ...
    def clear_security_events(self) -> None: ...

    # Layer 4: 发现结果
    def insert_finding(self, rule_id: str, severity: str, ...) -> None: ...
```

### 7.3 收敛管线实现

```python
class Planner:
    def plan(self, vuln_type: str) -> List[Candidate]:
        spec = VULN_TYPE_SPECS[vuln_type]

        # 1. Seed
        candidates = self.seed_candidates(spec.seed_event_type)

        # 2. Filter chain
        for filter_impl in self.get_filters(spec.filter_chain):
            candidates = filter_impl.apply(candidates)
            if not candidates:
                break

        # 3. Dedup
        candidates = self.deduplicate(candidates)

        # 4. Rank + Cap
        candidates = self.rank(candidates)
        return candidates[:self.max_candidates]  # 默认 30

    def get_filters(self, chain_name: str) -> List[Filter]:
        chains = {
            "null-deref": [
                NonNullableFilter(),
                ArrayOOBPrecedenceFilter(),
                NullableSourceFilter(),
                CallReachFilter(self.store),
                GuardFilter(self.store),
                SafeFunctionFilter(),
                BoundsCheckFilter(self.store),
            ],
            "memory-leak": [
                CallReachFilter(self.store),
                SafeFunctionFilter(),
                MemoryReleaseFilter(self.store),
            ],
            "default": [
                CallReachFilter(self.store),
                SafeFunctionFilter(),
                BoundsCheckFilter(self.store),
            ],
            # ...
        }
        return chains.get(chain_name, chains["default"])
```

### 7.5 关键注意事项

1. **`security_events` 是瞬态表**：每轮扫描开始时清空，不是用户可见结果
2. **AI Agent 禁止查 `security_events`**：只能看收敛后的证据包
3. **CWE 白名单**：只接受 15 个 CWE，其他需作为 observation 报告
4. **递归 CTE 可达性**：`call_reach` 过滤器用递归 CTE 计算传递闭包，这是最关键的过滤步骤
5. **CFG 敏感分析**：`lifetime` 过滤器需要构建 CFG 来消除 use-after-free 误报
6. **跨过程分析**：`function_summary` 表存储函数摘要，用于 use-after-free 和 double-free 的跨过程推理
7. **安全函数/包装器列表**：维护两个列表，在 `safe_function_exclude` 过滤器中使用
8. **`latest` 符号链接**：`scans/latest` → `scans/<scan_id>`，CI/CD 可从固定路径读取最新结果
