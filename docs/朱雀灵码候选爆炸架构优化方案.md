## 1. 背景与问题定义

### 1.1 问题现象

朱雀灵码（SecGuardian）在实际运行中遇到了 **候选爆炸（Candidate Explosion）** 问题：

- **null_dereference** 场景产生的候选数量最多，是候选爆炸的重灾区
- 已尝试多轮优化，均未能有效收敛
- AI Agent 被大量候选淹没，推理质量下降

### 1.2 当前架构

```
Tree-Sitter
    ↓
Repository Facts（静态事实集合）
    ↓
Skill（30+ 安全技能）
    ↓
AI Agent（推理引擎）
```

### 1.3 核心矛盾

当前 `Repository Facts` 的本质是：

> **Repository = 静态事实集合**

它只回答"代码里有什么"，但不回答"它们之间如何关联"。导致 AI Agent 收到的候选缺乏语义关系过滤，候选数量无法收敛。

## 2. 根因分析

### 2.1 候选爆炸的根本原因

| 层面 | 问题 |
|------|------|
| 数据模型 | Repository Facts 仅有事实，无关系（无 Call Graph、无 Data Flow） |
| 过滤机制 | 缺少多层语义过滤，候选直接全量送入 AI Agent |
| 架构边界 | Skill 既拥有知识（数据表）又拥有推理规则，导致数据模型被漏洞类型驱动 |

### 2.2 漏洞驱动的数据模型陷阱

初始 Schema v0.1 按漏洞类型建表：

```
null_sources
null_guards
dereference_sites
free_sites          ← 如果扩展 double_free
double_free_sites   ← 如果扩展 double_free
malloc_sites        ← 如果扩展 memory_leak
leak_paths           ← 如果扩展 memory_leak
buffer_access_sites ← 如果扩展 buffer_overflow
overflow_sites       ← 如果扩展 buffer_overflow
```

若 30 个 Skill 每个都扩展自己的专项表，数据库将演变为：

```
repository_facts.db
├── null_xxx
├── memory_xxx
├── resource_xxx
├── buffer_xxx
├── crypto_xxx
└── ...（灾难）
```

这是典型的 **SAST Rule Database Anti-Pattern**。成熟工具不会这么设计。

## 3. 架构演进方向

### 3.1 核心升级

> **从**: Repository = 静态事实集合
> **到**: Repository = 可查询的程序语义图谱

### 3.2 技术选型

**选择**: SQLite + Graph Table 模型

**不选**: Neo4j

| 决策因素 | 说明 |
|----------|------|
| 安全扫描是批处理 | 不需要图数据库的实时遍历能力 |
| 查询模式固定 | SQL 足点查询足够，不需要 Cypher |
| Agent Pipeline 更适合 SQL | 管道式数据流天然契合 SQL |
| SQLite 随项目携带 | 零部署成本，单文件数据库 |
| 后续可导出 Graph View | 需要时再导出为图可视化，不绑定存储引擎 |

### 3.3 重要约束

> 不要一开始就做 CodeQL 那种全量关系图，否则容易陷入"造一个小型编译器"。

第一阶段聚焦：**C 语言 + Null Dereference 场景**，逐步扩展。

### 3.4 命名决策

| 项目 | 命名 | 理由 |
|------|------|------|
| 数据库 | `sgre.db` | SecGuard Repository Engine 的缩写 |
| 引擎概念 | Repository Engine (RE) | 描述职责而非能力，"Intelligence"被严重滥用 |
| 架构名称 | AI-Augmented Program Security Analysis Platform | 不叫"AI Native SAST"，定位为增强型分析平台 |

> **命名原则**: RE 描述的是"职责"（Index / Semantic Graph / Facts / Query / Planning），而不是"能力"（Intelligent / Smart / Cognitive）。未来 AI Agent 更强则 RE 提供更好上下文，推理模型更弱则 RE 仍提供确定性事实，增加规则则 RE 不变化——这个定位更稳。

## 4. 核心架构原则

### 原则一：按"程序事实类型"建表，不按"漏洞类型"建表

数据库表结构应与漏洞类型无关。漏洞逻辑由 Skill 的查询表达，不由表结构承载。

### 原则二：Skill 是消费者，不是数据模型污染者

```
Skill
  |
  | 查询（Query）
  |
  v
Repository Semantic Graph（sgre.db）
```

> **Skill 不应该拥有知识，Skill 应该拥有推理规则。**

守住这个边界，30 个 Skill 甚至 300 个 Skill 都不会污染底层。数据库永远稳定。

### 原则三：AI Agent 是推理引擎，不是数据发现引擎

AI Agent 的职责是对已收敛的证据包进行推理判断，而非从海量候选中自行发现线索。数据发现由 Repository Engine 的查询层完成。

### 原则四：分层稳定，上层可变

- **Program Facts Layer**: 最稳定，不因增加 Skill 而改变
- **Semantic Graph Layer**: 稳定，关系类型通过 edge_type 扩展而非建表
- **Security Evidence Layer**: 中等稳定，事件类型通过 event_type 扩展而非建表
- **Finding Layer**: 可变，AI Agent 输出层

## 5. 四层数据模型设计

### 5.1 模型全景

```
Repository Engine (sgre.db)
    │
    ├── Layer 1: Program Facts（稳定核心，与漏洞无关）
    │     ├── files
    │     ├── functions
    │     ├── variables
    │     ├── expressions
    │     ├── types
    │     └── locations
    │
    ├── Layer 2: Semantic Graph（关系层，统一图模型）
    │     ├── graph_nodes
    │     └── graph_edges
    │
    ├── Layer 3: Security Evidence（证据层，统一事件模型）
    │     └── security_events
    │
    └── Layer 4: Findings（发现层，AI Agent 输出）
          └── findings
```

### 5.2 各层职责

| 层 | 职责 | 稳定性 | 扩展方式 |
|----|------|--------|----------|
| Layer 1 - Program Facts | 描述程序实体（函数、变量、表达式、类型、位置） | 最稳定 | 基本不扩展 |
| Layer 2 - Semantic Graph | 描述实体间关系（调用、数据流、所有权、控制流） | 稳定 | 新增 edge_type 值，不建表 |
| Layer 3 - Security Evidence | 记录安全相关事件（NULL值、资源分配、资源释放、解引用） | 中等稳定 | 新增 event_type 值，不建表 |
| Layer 4 - Findings | AI Agent 推理结论 | 可变 | 新增 rule_id 值 |

### 5.3 与初始 v0.1 的关键差异

| v0.1（漏洞驱动，已废弃） | v2.0（程序语义驱动） |
|--------------------------|----------------------|
| `null_sources` 表 | `security_events` + `event_type='NULL_VALUE'` |
| `null_guards` 表 | `security_events` + `event_type='NULL_GUARD'` |
| `dereference_sites` 表 | `security_events` + `event_type='DEREFERENCE'` |
| `function_calls` 表 | `graph_edges` + `edge_type='CALL'` |
| `data_flow_edges` 表 | `graph_edges` + `edge_type='DATA_FLOW'` |
| 每种漏洞新增一批表 | 每种漏洞仅新增 edge_type / event_type 枚举值 |

## 6. 数据库 Schema 详细设计

### 6.1 Layer 1: Program Facts

#### 6.1.1 files 表

```sql
CREATE TABLE files (
    id          INTEGER PRIMARY KEY,
    path        TEXT NOT NULL,
    language    TEXT DEFAULT 'c',
    checksum    TEXT,
    loc         INTEGER,
    created_at  INTEGER
);
```

#### 6.1.2 functions 表（核心实体）

```sql
CREATE TABLE functions (
    id           INTEGER PRIMARY KEY,
    file_id      INTEGER,
    name         TEXT,
    signature    TEXT,
    return_type  TEXT,
    is_static    BOOLEAN,
    start_line   INTEGER,
    end_line     INTEGER,
    FOREIGN KEY(file_id) REFERENCES files(id)
);
```

#### 6.1.3 variables 表

```sql
CREATE TABLE variables (
    id               INTEGER PRIMARY KEY,
    function_id      INTEGER,
    name             TEXT,
    type             TEXT,
    storage_class    TEXT DEFAULT 'auto',
    declaration_line INTEGER,
    is_pointer       BOOLEAN,
    is_nullable      BOOLEAN,
    source_kind      TEXT,
    FOREIGN KEY(function_id) REFERENCES functions(id)
);
```

> **`storage_class`**: 区分 `auto`（栈）/ `static`（静态/全局，C 标准零初始化）/ `register` / `heap`。`memory_uninitialized` 检测依赖此字段过滤掉无需检测的 `static` 变量。

#### 6.1.4 expressions 表

```sql
CREATE TABLE expressions (
    id           INTEGER PRIMARY KEY,
    function_id  INTEGER,
    text         TEXT,
    line         INTEGER,
    expr_type    TEXT,
    FOREIGN KEY(function_id) REFERENCES functions(id)
);
```

#### 6.1.5 types 表

```sql
CREATE TABLE types (
    id    INTEGER PRIMARY KEY,
    name  TEXT NOT NULL,
    kind  TEXT
);
```

#### 6.1.6 locations 表

```sql
CREATE TABLE locations (
    id       INTEGER PRIMARY KEY,
    file_id  INTEGER,
    line     INTEGER,
    column   INTEGER,
    FOREIGN KEY(file_id) REFERENCES files(id)
);
```

### 6.2 Layer 2: Semantic Graph

#### 6.2.1 graph_nodes 表

```sql
CREATE TABLE graph_nodes (
    id          INTEGER PRIMARY KEY,
    entity_type TEXT NOT NULL,
    entity_id   INTEGER NOT NULL,
    properties  TEXT
);
```

#### 6.2.2 graph_edges 表（统一关系表）

```sql
CREATE TABLE graph_edges (
    id          INTEGER PRIMARY KEY,
    src_id      INTEGER NOT NULL,
    dst_id      INTEGER NOT NULL,
    edge_type   TEXT NOT NULL,
    properties  TEXT,
    FOREIGN KEY(src_id) REFERENCES graph_nodes(id),
    FOREIGN KEY(dst_id) REFERENCES graph_nodes(id)
);
```

**edge_type 枚举（可扩展，不建表）**:

| edge_type | 含义 | 示例 properties |
|-----------|------|-----------------|
| `CALL` | 函数调用关系 | `{"call_line": 42}` |
| `DATA_FLOW` | 数据流传播 | `{"variable": "ptr"}` |
| `OWNERSHIP_TRANSFER` | 所有权转移 | `{"resource_kind": "memory"}` 或 `{"resource_kind": "resource", "resource_type": "file"}` |
| `RELEASE` | 释放关系 | `{"resource_kind": "memory"}` 或 `{"resource_kind": "resource", "resource_type": "socket"}` |
| `BRANCH` | 控制流分支 | `{"condition": "if(ptr)"}` |
| `ALIAS` | 别名关系 | `{"origin": "assignment"}` |

> **resource_kind 区分**: `"memory"` 表示堆内存所有权（malloc/free 体系），`"resource"` 表示系统资源所有权（文件/套接字/锁等）。详见 [6.3 内存与资源区分](#63-layer-3-security-evidence)。

> **扩展方式**: 新增漏洞类型只需新增 edge_type 枚举值，无需建新表。

### 6.3 Layer 3: Security Evidence

#### 6.3.1 security_events 表（统一事件表）

```sql
CREATE TABLE security_events (
    id          INTEGER PRIMARY KEY,
    event_type  TEXT NOT NULL,
    entity_id   INTEGER,
    location_id INTEGER,
    properties  TEXT,
    FOREIGN KEY(location_id) REFERENCES locations(id)
);
```

**event_type 枚举（可扩展，不建表）**:

#### 内存操作事件（Memory Events）

| event_type | 含义 | 示例 properties |
|------------|------|-----------------|
| `MEMORY_ALLOC` | 堆内存分配 | `{"allocator": "malloc", "zeroed": false, "size_expr": "n * sizeof(T)", "variable": "p"}` |
| `MEMORY_RELEASE` | 堆内存释放 | `{"deallocator": "free", "variable": "p"}` |

> 内存操作 API 体系: `malloc`/`realloc` → `free`（`zeroed: false`），`calloc` → `free`（`zeroed: true`），`new` → `delete`。对象是**同质的堆内存块**，无类型区分。
>
> **`zeroed` 属性**: `malloc` 分配的内存未清零（`zeroed: false`），`calloc` 分配的内存已清零（`zeroed: true`）。此属性是 `memory_uninitialized` 检测的关键依据。

#### 资源操作事件（Resource Events）

| event_type | 含义 | 示例 properties |
|------------|------|-----------------|
| `RESOURCE_ACQUIRE` | 系统资源获取 | `{"resource_type": "file", "acquire_api": "open", "variable": "fd"}` |
| `RESOURCE_RELEASE` | 系统资源释放 | `{"resource_type": "file", "release_api": "close", "variable": "fd"}` |

> 资源是**异质的**，每种资源类型有独立的获取/释放 API 对和生命周期语义。

**资源类型分类（resource_type 枚举）**:

| resource_type | 获取 API | 释放 API | 句柄类型 | 说明 |
|---------------|----------|----------|----------|------|
| `file` | `open` / `fopen` | `close` / `fclose` | `int fd` / `FILE*` | 文件描述符/文件句柄 |
| `socket` | `socket` | `close` | `int fd` | 网络套接字 |
| `lock` | `pthread_mutex_lock` | `pthread_mutex_unlock` | `pthread_mutex_t*` | 互斥锁 |
| `db_conn` | `connect` | `disconnect` | `conn*` | 数据库连接 |
| `pipe` | `pipe` | `close` | `int fd[2]` | 管道 |
| `mmap` | `mmap` | `munmap` | `void*` | 内存映射（注意：返回指针但需 munmap 释放，不是 free） |

> **mmap 是内存与资源的边界案例**: 返回 `void*` 看似内存，但必须用 `munmap` 释放而非 `free`。归入资源类，`resource_type: "mmap"`。

#### 其他安全事件

| event_type | 含义 | 示例 properties |
|------------|------|-----------------|
| `NULL_VALUE` | NULL 值来源 | `{"variable": "user", "origin": "return"}` |
| `DEREFERENCE` | 解引用操作 | `{"variable": "user", "expression": "user->name"}` |
| `NULL_GUARD` | NULL 检查守卫 | `{"variable": "user", "condition": "NULL_CHECK"}` |
| `BUFFER_ACCESS` | 缓冲区访问 | `{"buffer": "buf", "index_expr": "i"}` |
| `INTEGER_OP` | 整数运算 | `{"op": "add", "overflow_risk": true}` |

#### 值生命周期事件（Value Lifecycle Events）

> 以下事件描述变量/内存值的声明、读取、写入操作。这些是**通用程序操作**，不仅服务于 `memory_uninitialized`，也可被 use_after_free、data_flow 等其他分析复用。

| event_type | 含义 | 角色 | 示例 properties |
|------------|------|------|-----------------|
| `VARIABLE_DECLARE` | 变量声明 | 未初始化 Source | `{"variable": "x", "type": "int", "storage_class": "auto", "initialized": false}` |
| `VALUE_USE` | 值读取/使用 | Sink | `{"variable": "x", "expression": "y = x", "access": "direct"}` 或 `{"variable": "p", "expression": "*p", "access": "dereference"}` |
| `VALUE_INIT` | 值写入/初始化 | Sanitizer | `{"variable": "x", "expression": "x = 0", "init_kind": "assignment"}` 或 `{"variable": "p", "expression": "*p = 0", "init_kind": "pointer_write"}` |

**`storage_class` 枚举**:

| storage_class | 说明 | 默认初始化 | 需检测未初始化? |
|---------------|------|-----------|----------------|
| `auto` | 局部变量（栈） | 未初始化 | **是** |
| `static` | 静态/全局变量 | 零初始化（C 标准） | 否 |
| `register` | 寄存器变量 | 未初始化 | **是** |
| `heap` | 堆分配（通过指针） | 取决于 allocator | malloc 是，calloc 否 |

> **设计要点**: `VARIABLE_DECLARE` 仅对 `storage_class` 为 `auto`/`register` 且 `initialized: false` 的声明产生安全相关事件。`static` 变量由 C 标准保证零初始化，不需检测。堆内存的未初始化由 `MEMORY_ALLOC` 的 `zeroed` 属性标记。

#### 内存与资源区分的设计理由

| 维度 | 内存泄漏（Memory Leak） | 资源泄漏（Resource Leak） |
|------|------------------------|--------------------------|
| **对象类型** | 同质堆内存块 | 异质系统资源（文件/套接字/锁/连接...） |
| **API 体系** | malloc/free（固定一对） | 每种资源类型有独立 API 对 |
| **句柄类型** | `void*` / `T*`（指针） | `int fd` / `FILE*` / `mutex_t*`（多种句柄） |
| **分析焦点** | 所有权转移 + 可达性 | 获取/释放配对 + 全路径覆盖（尤其错误路径） |
| **错误路径** | 一般关注 | **高度关注**（资源泄漏主要发生在错误路径遗漏清理） |
| **系统影响** | 渐进退化，可能不崩溃 | 可能快速触及系统上限（如 fd 耗尽），更易即时失败 |
| **Skill 分离** | `memory_leak` Skill | `resource_leak` Skill |
| **事件类型** | `MEMORY_ALLOC` + `MEMORY_RELEASE` | `RESOURCE_ACQUIRE` + `RESOURCE_RELEASE` |

> **结论**: 两者在数据模型层面复用同一张 `security_events` 表（不建分表），但在 event_type 和 properties 层面做明确区分。两个 Skill 各自查询自己关注的事件类型，互不干扰。

> **扩展方式**: 新增漏洞类型只需新增 event_type 枚举值，无需建新表。

## 7. 候选收敛机制

### 7.1 四级过滤管道

```
初始候选: dereference_sites = 600
    │
    ├─ Filter 1: 有没有 nullable source?
    │    ↓
    │    200
    │
    ├─ Filter 2: Call Graph 是否可达?
    │    ↓
    │    80
    │
    ├─ Filter 3: Data Flow 是否传播?
    │    ↓
    │    30
    │
    ├─ Filter 4: 是否存在 Guard?
    │    ↓
    │    10
    │
    └─ 最终送入 AI Agent: 10 cases（而非 600 cases）
```

### 7.2 各过滤层职责

| 过滤层 | 查询对象 | 收敛效果 | 依赖数据 |
|--------|----------|----------|----------|
| Filter 1 - Nullable Source | security_events (NULL_VALUE) | 600 → 200 | Layer 3 |
| Filter 2 - Call Graph 可达性 | graph_edges (CALL) | 200 → 80 | Layer 2 |
| Filter 3 - Data Flow 传播 | graph_edges (DATA_FLOW) | 80 → 30 | Layer 2 |
| Filter 4 - Guard 存在性 | security_events (NULL_GUARD) | 30 → 10 | Layer 3 |

### 7.3 输出格式：Security Evidence Package

```json
{
  "type": "NULL_DEREFERENCE",
  "target": {
    "function": "foo",
    "line": 100
  },
  "evidence": [
    {
      "type": "nullable_source",
      "function": "get_user"
    },
    {
      "type": "call_path",
      "path": ["foo", "get_user"]
    },
    {
      "type": "missing_guard",
      "variable": "user"
    }
  ]
}
```

## 8. 多漏洞类型复用示例

### 8.1 Null Dereference

**代码**:
```c
User *u = get_user();
printf("%s", u->name);
```

**生成数据**:
- Event: `NULL_VALUE` (get_user 返回)
- Edge: `CALL` (foo → get_user)
- Event: `DEREFERENCE` (u->name)
- Edge: `DATA_FLOW` (get_user 返回值 → u)

**Skill 查询**: 寻找 `NULL_VALUE` + `DATA_FLOW` + `DEREFERENCE` 之间是否存在路径

### 8.2 Double Free

**代码**:
```c
p = malloc();
free(p);
free(p);
```

**生成数据**:
- Event: `MEMORY_ALLOC` (p, allocator: malloc)
- Event: `MEMORY_RELEASE` (p, deallocator: free)
- Event: `MEMORY_RELEASE` (p, deallocator: free)
- Edge: `OWNERSHIP_TRANSFER` (p owns heap_object, resource_kind: memory)

**Skill 查询**: 同一内存对象是否存在两个 `MEMORY_RELEASE`，中间没有重新 `MEMORY_ALLOC`

### 8.3 Memory Leak

**代码**:
```c
p = malloc();
return;  // 忘记 free
```

**生成数据**:
- Event: `MEMORY_ALLOC` (p, allocator: malloc)
- 无 `MEMORY_RELEASE`

**Skill 查询** (`memory_leak`): `MEMORY_ALLOC` 到 `MEMORY_RELEASE` 之间不存在路径（`NO_RELEASE_PATH`）

### 8.4 Resource Leak

**代码**:
```c
int fd = open("config.txt", O_RDONLY);
if (read(fd, buf, size) < 0) {
    return;  // 错误路径遗漏 close
}
close(fd);
```

**生成数据**:
- Event: `RESOURCE_ACQUIRE` (fd, resource_type: file, acquire_api: open)
- Edge: `BRANCH` (if read < 0)
- Event: `RESOURCE_RELEASE` (fd, resource_type: file, release_api: close) — 仅在正常路径

**Skill 查询** (`resource_leak`): `RESOURCE_ACQUIRE` 是否在**所有路径**（含错误路径）上都有对应的 `RESOURCE_RELEASE`

> **与 Memory Leak 的关键差异**: Resource Leak 高度关注**错误路径**上的遗漏清理。内存泄漏主要关注所有权可达性，资源泄漏主要关注获取/释放的**全路径配对**。

### 8.5 Memory Uninitialized（复杂场景——架构可行性反推）

> 此场景用于反推架构设计可行性。未初始化检测涉及栈/堆两类对象、声明-写入-读取三阶段生命周期、路径敏感分析，是验证四层模型通用性的关键用例。

#### 8.5.1 场景 A：栈变量未初始化

**代码**:
```c
int x;           // 声明未初始化（auto，栈）
int y = x;       // 使用未初始化值
```

**生成数据**:
- Event: `VARIABLE_DECLARE` (x, storage_class: auto, initialized: false) ← **Source**
- Event: `VALUE_USE` (x, expression: "y = x", access: direct) ← **Sink**
- Edge: `DATA_FLOW` (x → y)
- 无 `VALUE_INIT` 事件 ← **缺少 Sanitizer**

**Skill 查询** (`memory_uninitialized`):
```
寻找 VARIABLE_DECLARE(initialized=false)
  → DATA_FLOW
  → VALUE_USE
之间是否存在路径，且路径上无 VALUE_INIT 作为 Sanitizer
```

#### 8.5.2 场景 B：堆内存未初始化（malloc）

**代码**:
```c
int *p = malloc(sizeof(int));   // malloc 不清零
int y = *p;                      // 读取未初始化堆内存
```

**生成数据**:
- Event: `MEMORY_ALLOC` (p, allocator: malloc, zeroed: false) ← **Source**
- Event: `VALUE_USE` (p, expression: "*p", access: dereference) ← **Sink**
- Edge: `DATA_FLOW` (p → *p)
- 无 `VALUE_INIT` 事件 ← **缺少 Sanitizer**

**对比 calloc**:
```c
int *p = calloc(1, sizeof(int)); // calloc 清零
int y = *p;                       // 安全，值为 0
```
- Event: `MEMORY_ALLOC` (p, allocator: calloc, **zeroed: true**) ← Source 标记为已初始化，**不产生候选**

#### 8.5.3 场景 C：路径敏感（条件初始化）

**代码**:
```c
int x;                // 声明未初始化
if (cond)
    x = 1;            // 仅 cond 为真时初始化
use(x);               // cond 为假时使用未初始化值
```

**生成数据**:
- Event: `VARIABLE_DECLARE` (x, initialized: false) ← Source
- Edge: `BRANCH` (if cond)
- Event: `VALUE_INIT` (x, init_kind: assignment) ← Sanitizer（仅在 cond 分支）
- Event: `VALUE_USE` (x) ← Sink

**Skill 查询**: 是否存在从 `VARIABLE_DECLARE` 到 `VALUE_USE` 的路径，该路径上**没有**经过 `VALUE_INIT`（即 cond=false 分支）

> **架构可行性验证**: 此场景需要**路径敏感分析**（path-sensitive），与 Null Dereference 的 Guard 检查同构。当前架构通过 `BRANCH` edge + 路径查询可表达此问题，但精确求解需要 CFG（已在硬骨头 Section 10 中标注）。**架构方向可行，精度待 CFG 落地后提升。**

#### 8.5.4 场景 D：跨函数初始化（interprocedural）

**代码**:
```c
void init(int *p) { *p = 0; }
void foo() {
    int x;           // 声明未初始化
    init(&x);        // 通过指针参数初始化
    use(x);          // 安全——但需要跨函数分析才能确认
}
```

**生成数据**:
- Event: `VARIABLE_DECLARE` (x, initialized: false)
- Edge: `CALL` (foo → init)
- Function Summary: init → `{"param_0": "initialized_by_write"}`
- Event: `VALUE_USE` (x)

**Skill 查询**: `VARIABLE_DECLARE` → `CALL`(init) → `VALUE_USE`，检查 `function_summary` 中 init 是否标记参数为已初始化

> **架构可行性验证**: `function_summary` 表已设计（Section 6.5），可承载跨函数初始化契约。**架构支持此场景，但依赖 function_summary 的自动推断精度。**

#### 8.5.5 场景 E：部分初始化（结构体字段）

**代码**:
```c
struct Foo { int x; int y; };
struct Foo f;        // 所有字段未初始化
f.x = 0;             // 仅 f.x 初始化
use(f.y);            // f.y 仍未初始化
```

> **设计差距发现**: 当前 `VARIABLE_DECLARE` 和 `VALUE_INIT` 事件以**变量**为粒度，无法表达结构体**字段级**初始化状态。需要 `field` 属性支持字段敏感分析。
>
> **补充设计**: `VALUE_INIT` 的 properties 增加 `field` 字段：`{"variable": "f", "field": "x", "init_kind": "field_write"}`。`VALUE_USE` 同理：`{"variable": "f", "field": "y", "access": "field_read"}`。

#### 8.5.6 候选收敛管道（memory_uninitialized 专用）

```
初始候选: 所有 VALUE_USE 事件 = N
    │
    ├─ Filter 1: 值来源是否未初始化?
    │    (VARIABLE_DECLARE initialized=false 或 MEMORY_ALLOC zeroed=false)
    │    ↓
    │    N1
    │
    ├─ Filter 2: DATA_FLOW 从未初始化 Source 到 Use 是否可达?
    │    ↓
    │    N2
    │
    ├─ Filter 3: 是否所有路径上都存在 VALUE_INIT (Sanitizer)?
    │    ↓
    │    N3（这些是真正的未初始化使用）
    │
    └─ 最终送入 AI Agent: N3 cases
```

> **与 Null Dereference 的同构性**: 两者都是 Source → DataFlow → Sink + Sanitizer 模式。候选收敛管道结构完全一致，验证了架构的通用性。

### 8.6 复用总结

| 漏洞类型 | Skill | 复用的事件 | 复用的关系 | 新增表 |
|----------|-------|-----------|-----------|--------|
| Null Dereference | `null_dereference` | NULL_VALUE, DEREFERENCE, NULL_GUARD | CALL, DATA_FLOW | 无 |
| Double Free | `double_free` | MEMORY_ALLOC, MEMORY_RELEASE | OWNERSHIP_TRANSFER | 无 |
| Memory Leak | `memory_leak` | MEMORY_ALLOC, MEMORY_RELEASE | DATA_FLOW | 无 |
| Resource Leak | `resource_leak` | RESOURCE_ACQUIRE, RESOURCE_RELEASE | BRANCH, DATA_FLOW | 无 |
| Memory Uninitialized | `memory_uninitialized` | VARIABLE_DECLARE, VALUE_USE, VALUE_INIT, MEMORY_ALLOC(zeroed) | DATA_FLOW, BRANCH, CALL | 无 |
| Use After Free | `use_after_free` | MEMORY_RELEASE, VALUE_USE, DEREFERENCE | OWNERSHIP_TRANSFER, DATA_FLOW | 无 |
| Buffer Overflow | `buffer_overflow` | BUFFER_ACCESS | DATA_FLOW | 无 |

> **所有漏洞类型复用同一套表结构，仅通过 event_type / edge_type 枚举值区分。内存操作与资源操作通过不同 event_type 明确区分，两个 Skill 各查各的事件，互不干扰。**
>
> **`memory_uninitialized` 反推结论**: 该场景是当前最复杂的用例（涉及栈/堆双对象、声明-写入-读取三阶段、路径敏感、跨函数、字段敏感），但完全映射到现有四层模型，无需新增表。仅需新增 3 个 event_type（`VARIABLE_DECLARE`/`VALUE_USE`/`VALUE_INIT`）和 `variables.storage_class` 字段。**架构设计可行性得到验证。**

## 10. 硬骨头与压力测试

> 不要过早认为 AI + RE 一定超过 Coverity。以下三个硬骨头必须正视。

### 10.1 Data Flow 精度（最大挑战）

**问题示例**:
```c
char *p;
if (condition)
    p = a;
else
    p = b;
*p;  // 需要知道 p 可能来自 a，也可能来自 b
```

**现状**: Tree-Sitter 无法解决此问题。

**需要**: CFG + SSA + Points-to Analysis

### 10.2 Path Explosion（路径爆炸）

**问题示例**:
```c
if (a) {
    if (b) {
        if (c) {
            // 路径指数增长
        }
    }
}
```

**现状**: 传统 SAST 花了 20 年以上解决此问题。

**定位**: AI Agent 可以帮助解释路径，但不能替代底层路径分析。

### 10.3 False Positive 控制

**核心矛盾**: "发现问题"和"证明问题"差距巨大。

**关键问题**: 安全工具最后拼的是"为什么相信这个漏洞是真的？"

**应对**: 这正是 Evidence Layer 的价值——提供可追溯的证据链，而非仅给出告警。

### 10.4 路径敏感与字段敏感（memory_uninitialized 反推发现）

> `memory_uninitialized` 场景反推出两个当前架构可表达但精度不足的分析需求。

**路径敏感（Path-Sensitivity）**:
```c
int x;
if (cond) x = 1;   // 仅一条路径初始化
use(x);             // 另一条路径未初始化
```
当前架构通过 `BRANCH` edge + 路径查询可**表达**此问题，但精确求解需要 CFG。与 Null Dereference 的 Guard 检查面临同一挑战。

**字段敏感（Field-Sensitivity）**:
```c
struct Foo f;
f.x = 0;        // f.x 已初始化
use(f.y);       // f.y 仍未初始化
```
当前 `VALUE_INIT`/`VALUE_USE` 事件需增加 `field` 属性支持字段级区分。否则只能保守报告整个结构体未初始化，误报率高。

**定位**: 这两个需求不破坏架构（无需新表），但提示 CFG 和字段敏感分析是提升精度的必要投入。

### 12.1 架构管道

```
Tree-sitter Indexer
    ↓
Repository Parser
    ↓
Semantic Graph Builder
    │
    ├── Function Graph
    └── Security Facts

Candidate Planner
    ↓

```

### 12.2 Scope 定义

**Included（第一阶段）**:
- Function Model
- Call Graph
- Pointer Object Discovery
- Null Source Detection
- Dereference Sink Index
- Null Guard Index
- Function Summary

**Not Included（第一阶段）**:
- Full CFG
- SSA
- Alias Analysis
- C++ Support

### 12.3 分阶段实施

| Phase | 名称 | 输入 | 输出 | 验收标准 |
|-------|------|------|------|----------|
| Phase 1 | Function Extraction | Tree-sitter AST | functions 表 | 100% C 函数索引 |
| Phase 2 | Call Graph Builder | functions | graph_edges (CALL) | 调用图查询可用 |
| Phase 3 | Pointer Analysis | AST | variables + graph_edges (DATA_FLOW) | 指针声明/赋值/返回检测 |
| Phase 4 | Null Source Detector | functions | security_events (NULL_VALUE) | return NULL / malloc / external API |
| Phase 5 | Dereference Detector | functions | security_events (DEREFERENCE) | ptr->field / (*ptr) / ptr[index] |
| Phase 6 | Null Guard Detector | functions | security_events (NULL_GUARD) | if(ptr) / if(ptr==NULL) / if(NULL==ptr) |
| Phase 7 | Candidate Planner | 全层查询 | Security Evidence Package | 四级过滤管道运行 |

### 12.4 首批任务建议

> **第一批 Agent 任务只做 Phase 1 + Phase 2：Function Model + Call Graph**

**原因**:
- 这是整个 Repository Semantic Graph 的骨架
- 如果 Call Graph 不稳定，后面的 Null / DataFlow 都是在沙滩上盖楼
- Tree-Sitter 已有 AST 基础，补 Call Graph 的投入产出比最高

**Unit Test**:
- Function extraction
- Call graph
- Null source
- Dereference
- Guard

**Security Test Cases**:
- NULL return
- Malloc failure
- Missing check
- Checked pointer
- Interprocedural propagation
- Memory leak - malloc without free
- Memory leak - error path missing free
- Resource leak - file open without close
- Resource leak - error path missing close

## 13. 未来扩展方向

| 漏洞类型 | Skill | 所需新增 | 依赖图模型 |
|----------|-------|----------|-----------|
| Buffer Overflow | `buffer_overflow` | event_type: BUFFER_ACCESS | Array Index Graph |
| Use After Free | `use_after_free` | event_type: MEMORY_RELEASE + VALUE_USE | Ownership Graph |
| Memory Leak | `memory_leak` | event_type: MEMORY_ALLOC + MEMORY_RELEASE | Ownership / Reachability |
| Resource Leak | `resource_leak` | event_type: RESOURCE_ACQUIRE + RESOURCE_RELEASE | Resource Lifecycle Graph（全路径配对） |
| Memory Uninitialized | `memory_uninitialized` | event_type: VARIABLE_DECLARE + VALUE_USE + VALUE_INIT; variables.storage_class; MEMORY_ALLOC.zeroed | Data Flow + Branch（路径敏感） |
| Integer Overflow | `integer_overflow` | event_type: INTEGER_OP | Data Flow |

> **扩展方式**: 仅新增 event_type / edge_type 枚举值 + 对应 Skill 查询逻辑，不新增数据库表。
>
> **内存与资源分离**: `memory_leak` 查询 `MEMORY_ALLOC`/`MEMORY_RELEASE` 事件，关注所有权可达性；`resource_leak` 查询 `RESOURCE_ACQUIRE`/`RESOURCE_RELEASE` 事件，关注全路径（含错误路径）的获取/释放配对。两者复用同一张 `security_events` 表，通过 event_type 隔离。
>
> **未初始化检测**: `memory_uninitialized` 查询 `VARIABLE_DECLARE`(initialized=false) + `MEMORY_ALLOC`(zeroed=false) 作为 Source，`VALUE_USE` 作为 Sink，`VALUE_INIT` 作为 Sanitizer。与 Null Dereference 的 Source-Flow-Sink-Sanitizer 模式同构。
