# secguard-clang 函数入参验证需求落地指南

> 目标：指导 Codex / AI Agent 在现有 secguard-clang 仓库中，落地“函数入口状态校验 / 隐式契约缺失”检测能力。
>
> 本文是实施指南，不预设仓库中尚未核实的目录、接口、数据结构或检测器实现。实施前必须先调研并遵循现有架构，优先增量复用，不得另起一套平行框架。

## 1. 背景与问题定义

secguard-clang 目前以 CWE 为主要缺陷分类和检测组织方式。现网出现了一类问题：函数使用输入对象及其关联状态前，缺少必要的入口校验。它不一定能被简单归结为某个确定的 CWE；只有当证据表明存在可达的空指针解引用等具体缺陷时，才应归入相应 CWE 告警。

### 1.1 问题案例

错误示例（现场片段）：

```c
int import_dn_group_tree_refresh(
    Nac_LdapSearchAckMsg_t *resp,
    import_para_ext_t *para)
{
    ldap_usrgroup_node_t *tree =
        (ldap_usrgroup_node_t *)(resp->group_data);

    if ((para->search_index != INVALID_SEARCHDN_IDX) &&
        (import_get_dn_level_diff(
            para->orig->base_dn, para->search_dn) > 1)) {
        char basepath[USER_GROUP_NAME_LEN_MAX + 1];
        if (import_get_base_path(
                para->orig->base_dn,
                para->search_dn,
                basepath, sizeof(basepath)) != 0) {
            return -1;
        }
        // ...
    }

    // ...
}
```

修复示例（问题单修改后的样子）：

```c
int import_dn_group_tree_refresh(
    Nac_LdapSearchAckMsg_t *resp,
    import_para_ext_t *para)
{
    ldap_usrgroup_node_t *tree =
        (ldap_usrgroup_node_t *)(resp->group_data);

    if (tree == NULL || resp->group_num == 0) {
        trace_debug(
            TRACE_IMPORT,
            "import dn group tree or group num invalid, group_num:%u.",
            resp->group_num);
        return 0;
    }

    if ((para->search_index != INVALID_SEARCHDN_IDX) &&
        (import_get_dn_level_diff(
            para->orig->base_dn, para->search_dn) > 1)) {
        char basepath[USER_GROUP_NAME_LEN_MAX + 1];
        if (import_get_base_path(
                para->orig->base_dn,
                para->search_dn,
                basepath, sizeof(basepath)) != 0) {
            return -1;
        }
        // ...
    }

    // ...
}
```

### 1.2 必须正确理解案例

修复补丁增加了两个前置条件：

- `tree != NULL`：分组树指针非空。
- `resp->group_num != 0`：分组数量非零。

不能仅凭补丁断言原代码必然发生 CWE-476（NULL Pointer Dereference）。完整函数的后续使用点、调用方、数据结构定义及接口约定尚需核实。`group_num == 0` 也不天然是错误；它是否应导致提前返回，取决于业务契约。

此外，原代码在检查 `tree` 之前就执行了 `resp->group_data`，因此若 `resp` 本身可能为 NULL，新增的 `tree == NULL` 判断无法保护对 `resp` 的首次解引用。`para`、`para->orig` 等对象同理，必须依据可达使用点与契约判断，不能机械添加检查。

## 2. 目标与非目标

### 2.1 目标

1. 在现有架构内识别函数入口缺少必要状态验证的高置信度问题。
2. 对指针、计数、长度、容量、状态字段及其关联约束进行有证据的分析。
3. 复用现有 `null-deref`、控制流、Repository Facts、Semantic Graph、SGRE 和 AI Agent 能力（以仓库实际实现为准）。
4. 区分确定性缺陷与需要业务语义判断的候选问题。
5. 对本案例建立可重复的正反例测试，避免只针对函数名或代码文本“硬编码识别”。
6. 让扫描结果包含可审查证据，并能通过既有告警状态与输出流程落地。

### 2.2 非目标

- 不把“所有指针参数必须判空”作为规则。
- 不把“所有计数器必须非零”作为规则。
- 不因本案例新建大量零散技能或重复 CWE Detector。
- 不将 `implicit-contract` 伪装成新的 CWE 编号；它是内部分析类别/能力名称，最终 CWE 映射必须有证据。
- 不重写 secguard-clang 的解析、事实库、语义图、漏斗或告警体系。
- 不在缺少业务证据时自动建议 `return 0`、`return -1` 或日志文案。
- 不因代码中没有显式判空就自动确认漏洞。
- 不假设 Tree-sitter AST 单独足以证明类型、别名、可达性或跨函数契约。

## 3. 推荐的能力边界与架构

采用“现有确定性检测 + 隐式契约候选分析 + AI 证据复核”的增量方案。

### 3.1 现有 `null-deref`：负责可证明的空指针解引用

当分析能证明或合理推断指针可能为 NULL，且存在可达解引用点（例如 `p->field`、`*p`、`p[i]` 等），继续由现有 `null-deref` 路径处理。

要求：

- 追踪指针定义、赋值来源、已知空值检查及控制流路径。
- 判断检查是否支配相关使用点，而非仅搜索同一函数是否出现 `p == NULL`。
- 尊重早退、条件分支、短路求值及路径约束。
- 已有防护如果在所有相关路径上有效，不应报错。
- 若现有分析无法证明可达解引用或 NULL 可达性，应降低为候选/需复核，而不是自动确认。
- 不要为了本需求复制一套平行 null-deref 实现。

### 3.2 新增/扩展 `implicit-contract` 能力：负责入口前置条件缺失

这是一个内部分析能力，用于发现“后续操作依赖某种状态，但入口或使用前缺少足够验证”的候选问题。先调研仓库现有 Contract / implicit-contract 相关设计；若已有能力，应扩展而不是新建重复实现。

第一阶段重点支持：

- **指针—使用关系**：指针可能为空，后续操作要求其非空。
- **指针—计数关系**：如 `group_data` 与 `group_num` 的关系，但必须由代码证据或契约支持。
- **指针—长度/容量关系**：指针、长度、容量组合必须满足的条件。
- **状态—操作关系**：状态字段决定后续操作是否合法。
- **返回值/错误状态关系**：调用结果未验证而继续使用，仅在契约证据充分时分析。

每条候选必须回答：
1. 后续哪一项操作依赖某个前置条件？
2. 该前置条件从哪里得到（类型、调用方、结构体约定、相邻代码、同类实现、文档或已配置契约）？
3. 哪条路径上缺少验证？
4. 缺少验证是否可能导致实际错误，而不是仅仅不符合某种编码风格？
5. 哪些证据支持告警，哪些关键证据仍缺失？

### 3.3 AI Agent 复核：负责业务语义，不代替确定性分析

AI 输入应尽量结构化，而不是只发送整段源码。优先提供：

- 函数签名及相关函数体片段；
- 参数与结构体字段的类型/定义（若可得）；
- 相关变量定义、赋值来源、别名信息（若可得）；
- 关键使用点及其控制流上下文；
- 已识别的 null-check / count-check / early return；
- 调用方、同类函数、已配置契约（若可得）；
- SGRE/静态分析给出的事实与不确定性；
- 候选缺陷类型和拟映射的 CWE（仅作候选，不强迫模型接受）。

AI 复核结果必须采用受控状态，例如沿用项目现有的 `Confirmed`、`Suspected`、`Dismissed` 或等价状态；先检查仓库当前状态枚举和 schema，不得擅自新增同义状态。

建议决策原则：

- **Confirmed**：有明确的使用点、可达路径及充分的契约/缺陷证据。
- **Suspected / AI_REQUIRED**：存在合理风险，但业务约定、路径或数据来源证据不足。
- **Dismissed**：有证据证明路径不可达、前置条件已由其他有效路径保证，或该状态合法且不构成缺陷。
- **不确定**：使用项目现有的需复核机制；禁止为了追求自动确认率强行定性。

AI 不应仅根据“修复代码增加了检查”推导原代码一定存在漏洞。补丁是重要线索，不是完整证明。

## 4. 分析流程

建议按以下顺序集成到现有漏斗，不预设具体层数或文件名：

1. **解析与事实提取**
   - 提取函数参数、局部指针赋值、结构体字段访问、比较条件、早退、返回值及相关使用点。
   - 尽可能复用已有 Tree-sitter AST、Repository Facts、Semantic Graph。
   - 对类型、别名、宏、条件编译或解析不完整的场景标记分析限制。

2. **候选触发**
   - 检测入口对象被读取、指针被解引用、计数/长度控制循环或访问、状态字段影响操作等模式。
   - 候选触发不是漏洞结论；不得把“缺少 if 检查”直接转为告警。
   - 避免单纯按参数名（如 `resp`、`tree`）或函数名进行规则匹配。

3. **控制流与路径分析**
   - 判断已有校验是否支配所有相关使用点。
   - 识别 guard clause、嵌套条件、短路表达式、反向条件、早退与错误分支。
   - 仅当仓库现有能力支持时才作路径结论；不能证明时明确降级。

4. **契约证据收集**
   - 搜索结构体定义、初始化/赋值来源、调用方的前置校验、同类函数、注释和已有契约。
   - 区分“显式证据”“间接证据”“未知”。不能把命名猜测当成契约。

5. **风险判断与 CWE 映射**
   - 可达的 NULL 解引用有充分证据时，映射 CWE-476。
   - 不当输入验证只有在输入约束和违反行为成立时，才考虑 CWE-20。
   - 若只有业务前置条件不明，输出内部 `implicit-contract` 候选类别，暂不强制映射 CWE。
   - 不允许为凑 CWE 编号而虚构缺陷。

6. **AI 复核**
   - 仅对有价值且静态分析未能定论的候选触发，遵循现有模型调用预算和去重机制。
   - 要求模型给出证据、反证、缺失信息及置信度/状态；置信度格式必须复用项目现有 schema。
   - 不要把完整仓库源码无差别发送给模型；采用相关上下文和按需扩展。

7. **告警归并与输出**
   - 同一根因的 CWE 告警与 implicit-contract 候选应按现有机制去重或关联，避免同一问题多条噪声告警。
   - 输出函数、位置、相关变量、使用点、缺少的前置条件、路径依据、证据来源、限制和修复方向。
   - 修复建议应描述需要满足的契约，不得无依据地替用户决定空输入时应返回 0 还是错误码。

## 5. 本案例应生成什么结果

实施前必须补齐完整函数、相关结构体和调用方证据。基于当前片段，系统最多应形成如下候选分析：

### 候选 A：`tree` 可能为空而后续被使用

- 来源：`resp->group_data`。
- 已知事实：转换本身不会保证指针非空。
- 待查事实：后续是否存在可达解引用；调用方是否保证 `resp` 和 `group_data` 有效；接口是否允许空分组。
- 结果规则：若能证明 NULL 可达且存在可达解引用，走 `null-deref` 并考虑 CWE-476；否则仅保留有证据的候选或不报。

### 候选 B：`group_num == 0` 时后续处理可能违反业务契约

- 来源：`resp->group_num`。
- 已知事实：修复补丁在计数为零时提前返回。
- 待查事实：零分组是否为合法空结果；后续循环、索引、树操作是否依赖正计数；接口文档或调用方是否建立该约束。
- 结果规则：只有证据证明零计数状态下后续操作不合法，才报告隐式契约问题；若只是“补丁加了判断”，不应自动报错。

### 其他入口风险

`resp`、`para`、`para->orig`、`base_dn`、`search_dn` 等访问也可能需要契约分析，但必须以可达使用、真实可空性和函数契约为依据。不能因为本案例增加了 `tree` 判空，就机械扩展为对所有参数报空指针风险。

## 6. 检测输出规范

必须复用仓库已有告警 schema、路径格式、状态和 severity 定义。若当前 schema 支持，建议为每条候选保留以下信息：

- `rule_id` / 内部能力名；
- `cwe_id`（可为空；仅有充分证据时填）；
- `function`、源文件和行号；
- `subject`：被验证的对象或状态；
- `required_condition`：后续操作要求的前置条件；
- `use_site`：依赖该条件的操作位置；
- `path_evidence`：为何该路径可达、已有保护为何不足；
- `contract_evidence`：契约证据及来源；
- `counter_evidence`：可能的保护、合法空状态或反证；
- `limitations`：缺失的类型、调用方、宏或跨函数信息；
- `status`：使用当前项目状态枚举；
- `recommendation`：有条件、基于证据的修复方向。

不要在仓库已有 schema 不允许时直接添加上述字段；先分析兼容性和消费端影响，必要时采用现有 `evidence` 或 metadata 机制。

## 7. 误报控制要求

以下情况必须重点覆盖：

1. **前置校验在调用方完成**：调用方已证明参数非空，且契约传播可信时，不应仅因被调函数内部没有判空就报错。若当前跨函数能力不足，输出限制或降低置信度。
2. **校验存在于其他控制流路径**：不能只做文本搜索；检查 guard clause、早退、条件分支和支配关系。
3. **合法空输入**：空结果、零计数可能是正常业务语义。
4. **非空指针不等于有效对象**：不能把 NULL 检查等同于对象生命周期、边界、初始化或数据一致性检查。
5. **字段之间的关系不可臆测**：指针与计数器不必天然同步，必须有契约证据。
6. **宏、包装函数与自定义校验函数**：若静态分析无法理解，记录限制，不得假装已证明。
7. **日志不是防护**：日志本身不建立前置条件；必须分析条件与控制流行为。
8. **早退返回值有业务语义**：不能统一要求返回 `-1` 或 `0`。
9. **补丁推断偏差**：修复差异用于生成候选和测试，不直接作为告警判据。
10. **重复告警**：同一缺陷同时触发 `null-deref` 与契约分析时，尽可能关联根因，避免告警膨胀。

## 8. 测试计划与验收标准

先建立小而高价值的测试集，测试必须运行在仓库现有测试框架中。

### 8.1 正例：应检出或进入需复核

- 参数指针可能为空，之后在同一路径上可达解引用，且没有有效保护。
- 计数为零时后续操作明确要求正计数，并有契约或操作证据。
- 指针与长度的组合违反已有明确契约，且后续操作依赖该契约。
- 保护只覆盖部分路径，另一条可达路径仍存在风险。
- 参数来自未经验证的外部/上游数据，相关接口契约明确要求验证。

### 8.2 反例：不应误报

- 在所有相关使用点之前已有有效判空和终止路径。
- 调用方完成校验，且项目当前分析能力足以可靠传播该前置条件。
- 空数据是明确允许的业务状态，后续逻辑正确处理。
- 变量虽可能为空，但所有可达路径都不会解引用它。
- 只有命名或风格暗示，没有证据证明契约被违反。
- `group_data != NULL && group_num == 0` 等状态没有被契约定义为错误。

### 8.3 案例专属测试

至少为上述错误/修复片段建立配对 fixture，并增加变体：

- `resp == NULL`；
- `group_data == NULL`；
- `group_num == 0`；
- `group_data == NULL && group_num > 0`；
- `group_data != NULL && group_num == 0`；
- 在调用方已检查参数后调用；
- 检查仅在一个分支存在；
- 后续实际存在或不存在解引用；
- 合法空结果路径。

这些组合是测试输入，不预先代表业务错误。预期结果要根据每个 fixture 明确声明的契约和后续操作设定。

### 8.4 验收门槛

- 本案例正例能被识别，或能给出明确的“证据不足/需复核”结果；不能只靠函数名、变量名或完整代码文本匹配。
- 配对反例不会因缺少显式判空而一律报错。
- 已有 `null-deref` 行为没有回归，已有输出 schema 与状态兼容。
- 每条确认告警能指出具体使用点、路径证据和契约依据。
- 业务语义证据不足时，不自动升级为 Confirmed。
- 有测试覆盖候选生成、复核决策、告警去重及输出路径。
- 有运行结果、变更文件列表和已知限制的实施报告。
- 不以“新增规则数量”或“AI 确认率”作为单独成功指标；同时观察精确率、误报、漏报和每个候选的模型调用成本。

## 9. 分阶段实施建议

### 阶段 0：仓库调研（必须先做）

1. 阅读 README、架构文档和现有四层漏斗说明，以仓库实际实现为准。
2. 找到 `null-deref` Detector / SKILL、Contract 或 implicit-contract 相关实现、SGRE 事实与语义图接口、AI 复核流程、告警 schema 和测试框架。
3. 找到告警状态、severity、CWE 映射、输出目录和去重逻辑的权威定义。
4. 追踪当前案例中已有 `null-deref` 为什么没有覆盖该问题：是没有可达解引用、没有完整上下文、解析/事实不足，还是业务问题本身不属于可证明的 NULL 解引用。
5. 提交调研报告：现有可复用能力、具体缺口、最小修改范围、测试入口、兼容性风险。调研未完成前不要大规模编码。

### 阶段 1：最小可用实现

- 优先修复现有 `null-deref` 在该类场景中确认存在的缺陷（若确有缺陷）。
- 只实现一个最小的 implicit-contract 候选路径，优先覆盖指针与关联计数/长度状态。
- 证据不足时使用现有需复核状态。
- 建立案例配对测试与误报反例。

## 11. 实施完成的最终判断

这项需求的成功标准不是“让 AI 给每个函数都补上入参判空”，而是：

- 能识别有证据支持的入口契约缺失；
- 能把确定性空指针缺陷交给已有 `null-deref` 路径；
- 能识别指针、计数、长度、状态之间有证据的关联约束；
- 能对业务语义不确定的候选降级，而不是制造误报；
- 能用正反例证明规则有效；
- 能在不破坏 secguard-clang 既有架构与性能预算的前提下逐步扩展。

**首选落地路线：先查明当前案例为何未被发现，再修复现有检测缺口；只有传统 CWE 分析确实覆盖不到的部分，才增加最小的 `implicit-contract` 候选分析。**
