# secguard-clang 支持第三方库函数：需求分析与落地实施指南

## 1. 任务目标

请在 `secguard-clang` / `sgre` 中增强对第三方库 API 的理解，使现有检测器在分析 C/C++ 项目源码时，能够识别项目源码中调用的外部库函数，并正确推断：

1. **堆内存分配**：哪些调用会产生需要释放的堆内存；
2. **内存释放**：哪些调用释放对象，以及释放的对象类型/配对约束；
3. **所有权转移/借用**：哪些 API 在什么条件下接管对象所有权，哪些只保存借用引用；
4. **可能返回空指针的 API**：哪些返回值可能为 `NULL`，后续解引用前应检查；
5. **返回值与参数的关系**：返回的是新对象、输入参数的别名、内部借用指针，还是通过出参写回的指针。

这不是简单地向搜索关键词列表中追加函数名。目标是建立**可审计、可扩展、可验证的外部 API 语义模型**，让现有的内存泄漏、空指针解引用等检测器能够消费这些语义，并降低误报。

## 2. 当前问题与约束

当前 `sgre` 的函数索引主要来自项目源码 AST/语义分析，因此第三方头文件中声明、但没有项目内函数定义的函数可能不会进入项目函数索引。分析器在定位分配、释放、所有权转移和判空要求时，如果只搜索项目自定义函数，可能遗漏第三方 API，导致：

- 分配函数被遗漏，无法建立分配点；
- 释放函数被遗漏，误报内存泄漏；
- 所有权转移函数被遗漏，误判对象仍由调用方负责释放；
- “引用添加”与“所有权转移”混淆，导致释放时机和双重释放判断错误；
- 外部 API 返回值可能为 `NULL`，但未进入空指针检查路径；
- 把借用指针误判为新分配对象，或对不应释放的返回值提出错误建议。

**重要约束：**
- 不要求把第三方库的实现源码加入项目索引，也不能假设扫描机器安装了所有库的完整源码。
- 应优先采用明确、可测试的外部 API 语义元数据；项目 AST/调用点信息用于匹配和上下文推理。
- 不得因为函数名相似就推断语义。必须使用精确的函数标识与库/头文件/可选版本信息；遇到不确定的 API，保持未知状态。
- 不要将第三方函数伪装成项目内函数定义，也不要虚构其函数体、调用图或控制流。
- 不应把“搜索到函数名”直接当成“已证明发生分配/释放/所有权转移”。
- 兼容当前项目的语言、Go 版本、索引结构、检测流水线和现有测试约定；实施前先阅读仓库现状，避免另起一套平行框架。

## 3. 先调研，再实现

开始修改前，请先检查并在实施记录中回答：

1. `sgre` 当前如何索引函数声明、函数定义、调用点、参数、返回类型和跨文件引用？
2. 内存泄漏、空指针解引用检测器分别从哪里获取分配/释放/返回值判空信息？
3. 当前 `Source`、`Hint`、语义图、Repository Facts 或其他证据对象中，哪些字段可表达外部函数语义？
4. 现有规则是否已经存在 allocator/deallocator、ownership、nullable-return 或 API model 的概念？如存在，应扩展而不是重复造轮子。
5. `cJSON` 和 `libxml2` 的目标版本/API 声明是否存在差异？若仓库无法确定依赖版本，模型必须记录适用范围或保守处理。
6. 现有检测报告和测试如何区分“确认”“候选”“未知/需 AI 复核”？新语义必须沿用已有分级机制。

调研完成后再给出简洁的实施计划，随后直接实现、测试并总结，不要只输出建议或把关键设计决策全部推回给用户。

## 4. 建议的模型设计

请根据仓库现有架构选择最小且一致的实现方式。逻辑上至少要区分以下语义，具体字段名称遵循项目既有风格：

- **API 身份**：函数全名、所属库/头文件、适用版本或条件、匹配依据。
- **分配语义**：返回值分配、出参分配（如 `char **`）、分配失败条件、对应释放方式。
- **释放语义**：释放哪个参数/对象、是否允许 `NULL`、是否有专用释放函数、是否存在类型或生命周期约束。
- **所有权语义**：
  - `transfer-on-success`：成功时接管所有权；
  - `transfer-always`：无条件接管（只有文档/实现能够确认时才使用）；
  - `borrow`：仅保存/返回借用引用，不接管所有权；
  - `shared/reference`：创建引用或共享关系，不转移原对象所有权；
  - `unknown`：无法确认，禁止推断。
- **返回值语义**：可能为空、非空保证（仅在有可靠依据时）、新分配对象、输入参数别名、库内部借用对象、静态/线程局部或环境管理存储。
- **证据和置信级别**：模型来源、适用范围、证据类型；不要把未经验证的推断标为确定事实。

请避免将以上语义压缩成一个含义模糊的 `is_allocator` / `is_free` 布尔值。特别是“返回指针”“返回新分配指针”“转移所有权”是不同维度，不能相互替代。

### 4.1 匹配规则

- 首选精确函数名与已知库模型匹配。
- 若已有 AST 声明信息，可用声明来源、包含头文件、命名空间/类型信息增强判定；但不能要求头文件一定存在才能识别已知 API。
- 若同名函数可能来自项目自定义实现或其他库，优先使用可得的声明/符号来源消歧；无法消歧时标记为不确定，不应强套模型。
- API 模型应可由测试直接验证，并能被内存泄漏、空指针检测器共同复用。
- 对未建模的外部函数，不做激进猜测；保留现有行为，并允许后续增补模型。

## 5. 第一批 API 覆盖清单与语义要求

以下清单是首批支持目标。实现时必须核对对应库的官方 API 文档、头文件声明和当前版本差异；不要仅凭本清单中的类别名称机械实现。若官方语义与本文件描述存在差异，以可靠的一手资料为准，并在代码注释/测试中说明。

### 5.1 libxml2

#### A. 创建/产生对象的 API

| 函数 | 典型结果 | 对应释放/生命周期处理 | 空指针处理 |
|---|---|---|---|
| `xmlNewNode` | 新建 `xmlNode` | 通常由 `xmlFreeNode` 释放；若加入文档树，生命周期可能转由文档树管理 | 返回值可能为 `NULL` |
| `xmlNewDoc` | 新建 `xmlDoc` | `xmlFreeDoc` | 返回值可能为 `NULL` |
| `xmlReadMemory` | 解析并返回 `xmlDoc` | `xmlFreeDoc` | 返回值可能为 `NULL` |
| `xmlReadFile` | 解析并返回 `xmlDoc` | `xmlFreeDoc` | 返回值可能为 `NULL` |
| `xmlXPathNewContext` | 新建 XPath context | `xmlXPathFreeContext` | 返回值可能为 `NULL` |
| `xmlXPathEvalExpression` | 新建 XPath object/result | `xmlXPathFreeObject` | 返回值可能为 `NULL` |
| `xmlNewNs` | 新建 namespace 对象 | 需依据对象是否挂接到节点及 libxml2 生命周期规则处理；不得未经核验简单认定所有路径都应单独调用 `xmlFreeNs` | 返回值可能为 `NULL` |

特别注意：
- `xmlXPathNewContext` 与 `xmlXPathEvalExpression` 都是“可能返回空指针”的 API，但它们产生的对象类型和释放函数不同，不能用同一个释放配对。
- `xmlReadMemory` / `xmlReadFile` 返回的是文档对象，不能用 `xmlFreeNode` 释放整个文档。
- `xmlNewNode` 创建的节点一旦被挂接到文档/节点树，其所有权和最终释放路径需要结合具体 API 语义判断，不能只看最初的分配调用。

#### B. 释放 API

| 函数 | 释放对象/用途 | 模型要求 |
|---|---|---|
| `xmlFreeDoc` | 释放文档及其管理的树对象 | 与文档创建/解析 API 建立配对；不要再把文档树内节点误判为独立泄漏对象 |
| `xmlFreeNode` | 释放单个节点 | 区分独立节点和已由文档树管理的节点 |
| `xmlFreeNodeList` | 释放节点列表 | 不要误认为等价于 `xmlFreeNode` 的单节点语义 |
| `xmlFreeNs` | 释放 namespace 对象 | 考虑 namespace 与节点关联时的生命周期约束 |
| `xmlXPathFreeContext` | 释放 XPath context | 与 `xmlXPathNewContext` 配对 |
| `xmlXPathFreeObject` | 释放 XPath object/result | 与 `xmlXPathEvalExpression` 等产生的 XPath object 配对 |

#### C. 所有权/树结构操作

| 函数 | 语义要求 | 必须避免的错误推断 |
|---|---|---|
| `xmlDocSetRootElement` | 将节点设为文档根节点；核实返回值表示及根节点替换时旧根节点的处理方式。应建模树/文档关联和所有权变化 | 不能简单标记为“参数永久转移且函数无返回信息”；该函数可能返回旧根节点，必须处理替换情形 |
| `xmlAddChild` | 将子节点加入父节点；按官方语义建模树归属变化。需考虑合并相邻文本节点等特殊情况及返回值 | 不得假设传入节点在所有情况下都原样存活，也不得在失败/特殊路径中盲目断言所有权已转移 |
| `xmlAddSibling` | 将节点加入同级链表；按官方语义建模节点关系、返回值和特殊情况 | 不得仅凭函数被调用就确认调用方不再拥有原指针 |

所有权转移模型必须能够表达条件和结果。若现有引擎无法精确表示 `xmlAddChild` / `xmlAddSibling` 的特殊情况，应将其标记为“需要上下文/保守处理”，不要为了覆盖率而强行确认。

#### D. 返回指针、但不等同于分配的 API

| 函数 | 返回值含义 | Null-Deref 检查 | 内存泄漏模型 |
|---|---|---|---|
| `xmlDocGetRootElement` | 从文档取得根节点指针，通常是文档树中的借用节点 | 返回值可能为空，使用前需依据控制流判空 | 不应当作新分配对象，不应要求单独释放返回值 |
| `xmlNextElementSibling` | 获取后续元素兄弟节点 | 返回值可能为空（例如没有后续元素） | 不应当作新分配对象 |
| `xmlFirstElementChild` | 获取第一个元素子节点 | 返回值可能为空（例如没有元素子节点） | 不应当作新分配对象 |

这里必须区分“返回指针可能为空”和“返回值是堆分配对象”。所有返回指针都不意味着调用方需要释放。

### 5.2 cJSON

#### A. 创建/解析 API

| 函数 | 典型结果 | 对应释放/所有权要求 | 空指针处理 |
|---|---|---|---|
| `cJSON_CreateObject` | 新建 JSON object | 未转移时通常由 `cJSON_Delete` 释放；若成功添加到拥有它的父对象，则生命周期随父对象管理 | 返回值可能为 `NULL` |
| `cJSON_CreateArray` | 新建 JSON array | 同上 | 返回值可能为 `NULL` |
| `cJSON_CreateString` | 新建 JSON string item | 同上 | 返回值可能为 `NULL` |
| `cJSON_Duplicate` | 复制 JSON item/tree | 复制结果通常由 `cJSON_Delete` 释放；需核实 `recurse` 参数对复制内容的影响 | 返回值可能为 `NULL` |
| `cJSON_Parse` | 解析 JSON 并返回根 item | `cJSON_Delete` | 返回值可能为 `NULL` |
| `cJSON_GetObjectItem` | 查找对象中的 item，返回借用指针 | 不单独释放返回值；由所属 JSON tree 的生命周期管理 | 返回值可能为 `NULL`；大小写敏感性应与具体 API 版本/函数变体一致 |
| `cJSON_GetArrayItem` | 查找数组中的 item，返回借用指针 | 不单独释放返回值 | 索引无效或元素不存在时可能返回 `NULL` |

#### B. 释放 API

| 函数 | 语义 | 模型要求 |
|---|---|---|
| `cJSON_Delete` | 释放 item 及其拥有的子树/相关内容 | 与创建、解析、复制所得对象配对；不得对父树拥有的内部借用 item 再单独删除 |
| `cJSON_free` | 释放由 cJSON 对外返回、且按 cJSON API 约定需要调用该函数释放的缓冲区 | 不能把它无差别等同于 `cJSON_Delete`；它与 `cJSON_Delete` 释放的对象类型不同 |

#### C. 添加 item：所有权转移与引用的关键区别

| 函数 | 所有权语义 | 建模要求 |
|---|---|---|
| `cJSON_AddItemToArray` | 成功添加后，父数组接管 item 的所有权 | 仅在成功条件满足时标记转移；之后不应再把 item 当作独立、仍由调用方拥有的对象释放 |
| `cJSON_AddItemToObject` | 成功添加后，父对象接管 item 的所有权 | 同上；还应考虑添加失败时 item 是否仍归调用方负责 |
| `cJSON_AddItemReferenceToArray` | 添加的是引用项，不应将原 item 的所有权转移给目标数组 | 不得与 `cJSON_AddItemToArray` 使用同一所有权模型 |
| `cJSON_AddItemReferenceToObject` | 添加的是引用项，不应将原 item 的所有权转移给目标对象 | 不得误判原 item 的生命周期已转移 |

必须核实当前 cJSON 版本中这些函数的返回类型、失败语义和内存所有权保证。对于返回成功/失败状态的版本，所有权转移应绑定到成功分支，而不是看到调用表达式就无条件认定转移。

### 5.3 C 标准库 / GNU 扩展：堆分配 API

| 函数 | 分配方式 | 释放配对 | 关键条件 |
|---|---|---|---|
| `strdup` | 返回新分配的字符串副本 | `free` | 失败时可能返回 `NULL` |
| `strndup` | 返回新分配、长度受限的字符串副本 | `free` | 失败时可能返回 `NULL` |
| `asprintf` | 通过 `char **` 出参写入新分配的字符串 | 成功时由调用方使用 `free(*out)` 释放 | 检查返回值：非负通常表示成功；失败时必须按平台/实现契约处理出参，不能只把 `asprintf` 当成返回指针的 allocator |
| `vasprintf` | 与 `asprintf` 类似，使用 `va_list` | 成功时由调用方使用 `free(*out)` 释放 | 同样需要基于返回值建模成功/失败条件 |

关键要求：
- `asprintf` / `vasprintf` 的函数返回值是状态码，不是所分配的字符串指针。真正的分配结果通过 `char **` 出参传回。
- 应建立“成功分支—出参指针有效—后续 `free` 配对”的关系。
- 对失败分支中出参的具体状态应以目标平台和官方文档为依据；若无法保证，不要假设它一定是 `NULL` 或一定保持原值。
- `strdup` / `strndup` 的返回指针应与 `free` 配对；不得与 `xmlFree*` 或 `cJSON_Delete` 混用。

### 5.4 C 标准库：可能返回空指针，但不分配调用方所有的对象

| 函数 | 返回值语义 | Null-Deref 检查 | 不应推断的语义 |
|---|---|---|---|
| `strstr` | 返回输入字符串内部匹配位置的指针，未找到时返回 `NULL` | 返回值在解引用前应有有效性保证 | 不是新分配对象；不能对返回值单独 `free` |
| `strchr` | 返回输入字符串内部匹配位置的指针，未找到时返回 `NULL` | 同上 | 不是新分配对象 |
| `strrchr` | 返回输入字符串内部最后一次匹配位置的指针，未找到时返回 `NULL` | 同上 | 不是新分配对象 |
| `getenv` | 返回环境存储中的字符串指针，变量不存在时返回 `NULL`；存储生命周期/可修改性受实现和标准约束 | 返回值使用前应检查 | 不是调用方拥有的堆分配对象，不应直接 `free` |
| `setlocale` | 返回 locale 名称字符串指针；请求失败时可能返回 `NULL`，返回存储的生命周期/后续调用影响需遵循标准约束 | 返回值使用前应检查 | 不是调用方拥有的普通堆分配对象，不应直接 `free` |

这组 API 主要用于空指针检查和别名/借用语义，不能作为内存分配清单处理。

## 6. 分配/释放配对不是简单的一对一字符串映射

实现时至少要支持以下配对与生命周期关系：

| 产生对象/返回指针的 API | 主要释放 API | 额外约束 |
|---|---|---|
| `xmlNewDoc`、`xmlReadMemory`、`xmlReadFile` | `xmlFreeDoc` | 文档管理其树中的节点；释放文档会影响其所管理对象的生命周期 |
| `xmlNewNode` | `xmlFreeNode`，或在成功挂接树后由文档/树生命周期管理 | 必须跟踪树归属变化，避免独立释放与文档释放重复计算 |
| `xmlXPathNewContext` | `xmlXPathFreeContext` | 不可用 `xmlFreeDoc` 或通用 `free` 替代 |
| `xmlXPathEvalExpression` | `xmlXPathFreeObject` | 结果对象与 XPath context 是不同对象 |
| `xmlNewNs` | 依据 libxml2 对 namespace 的关联和生命周期规则处理，必要时保守标记 | 不要仅因名字含 `New` 就自动生成无条件释放要求 |
| `cJSON_CreateObject`、`cJSON_CreateArray`、`cJSON_CreateString`、`cJSON_Duplicate`、`cJSON_Parse` | `cJSON_Delete` | 成功加入拥有型父节点后，生命周期通常由父树管理 |
| `strdup`、`strndup` | `free` | 普通堆字符串 |
| `asprintf`、`vasprintf` 成功写入的出参 | `free` | 只有成功路径才建立有效分配事实 |
| `xmlDocGetRootElement`、`xmlFirstElementChild`、`xmlNextElementSibling`、`cJSON_GetObjectItem`、`cJSON_GetArrayItem`、`strstr`、`strchr`、`strrchr`、`getenv`、`setlocale` | **无通用释放配对** | 这些返回值可能为空，但不因此成为调用方拥有的分配对象 |

如果当前引擎暂时无法表示父对象管理子对象、条件所有权转移或借用别名，优先输出可解释的候选/需复核结果；不要把复杂语义降级成错误的“分配后必须释放”规则。

## 7. 检测器如何消费模型

### 7.1 内存泄漏检测

- 识别第三方 API 的分配事件，包含返回值分配与出参分配两种模式。
- 根据释放函数的对象类型和参数位置建立匹配关系，而不是只匹配变量名或函数名。
- 对所有权转移建模为状态变化：调用方拥有 → 转移成功后由接收方/父对象拥有。
- 处理别名、结构体字段、返回值赋值和分支路径时，沿用现有数据流/语义图能力；不要在本需求中贸然构建未经验证的全程序精确指针分析。
- 对“释放函数已调用”的证据，确认其释放的是同一对象或已被证明的别名；不能仅因同一作用域出现 `xmlFreeDoc` / `cJSON_Delete` / `free` 就判定所有分配均已释放。
- 区分释放函数不匹配、重复释放、释放后使用、父对象接管和单纯未释放等问题；若现有检测器暂不支持某类问题，本任务不应伪造检测能力。

### 7.2 Null-Deref 检测

- 对模型标记为“可能返回 `NULL`”的 API，将调用结果视为可能为空，除非调用点的控制流或已有可信契约证明其非空。
- 只有在结果指针后续被解引用、访问成员、传入要求非空的调用，或用于其他危险操作时，才按现有规则评估风险。
- 正确识别显式判空、早退、断言/宏、错误分支以及条件表达式等已有分析器支持的保护模式。
- 不能要求每个可能返回 `NULL` 的函数调用都必须立即判空：如果返回值没有被使用、只在安全的比较中使用，或已通过控制流证明非空，不应报告空指针解引用。
- `strstr` / `strchr` / `strrchr` 的返回值指向原字符串内部；`getenv` / `setlocale` 的返回值有特殊生命周期。这些信息可帮助解释指针来源，但不能凭此推断非空。
- 不要把“模型中可空”直接等价为“漏洞”。漏洞结论必须有后续危险使用和缺少有效保护的证据。

## 8. 推荐实施步骤

1. **仓库调研**：定位函数索引、外部调用解析、内存泄漏和 Null-Deref 的语义入口与测试方式。
2. **模型设计**：复用现有机制，定义最小可扩展的外部 API 模型；明确分配、释放、所有权、返回值可空性和别名语义彼此独立。
3. **第一批建模**：加入本文件列出的 API；对版本差异或语义不确定的函数标注限制，不能无依据强行确认。
4. **检测器集成**：让现有检测器消费同一模型，不要在每个 detector 中复制独立函数名清单。
5. **证据可追踪**：诊断结果应能说明命中的 API 模型、语义类别、关键调用点、成功/失败路径（若适用）以及判定依据。
6. **测试**：添加最小、可重复的正反例，覆盖语义、控制流和误报边界。
7. **回归**：运行仓库既有测试和相关 benchmark；比较变更前后的确认数、候选数、误报和漏报情况。
8. **文档**：更新 API 模型维护说明，明确如何新增库、函数、配对关系、版本条件和测试用例。

## 9. 必须新增的测试矩阵

请将测试写入仓库当前采用的测试框架和目录，不要只在文档中列举。每个语义类别至少应包含正例、反例和边界条件。

### 9.1 内存泄漏与释放配对

- `xmlReadMemory` 成功后在所有路径调用 `xmlFreeDoc`：不应报泄漏。
- `xmlReadMemory` 返回文档后未释放，且没有转移给其他生命周期管理者：应能报告候选/确认结果，级别遵循现有机制。
- `xmlXPathNewContext` 与 `xmlXPathFreeContext` 正确配对。
- `xmlXPathEvalExpression` 与 `xmlXPathFreeObject` 正确配对。
- 将 `xmlXPathEvalExpression` 的结果错误地交给 `xmlXPathFreeContext`，不得判为正确释放。
- `cJSON_Parse` 返回根 item 后调用 `cJSON_Delete`：不应报泄漏。
- `cJSON_CreateObject` 成功加入父对象后由父对象清理：不应把子对象误报为独立泄漏。
- `cJSON_AddItemToObject/Array` 的成功路径应体现所有权转移；失败路径不能无条件认定已转移。
- `cJSON_AddItemReferenceToObject/Array` 不应被当作原 item 的所有权转移。
- `strdup` / `strndup` 分配后 `free`：不应报泄漏；缺少释放时应按现有能力报告。
- `asprintf` / `vasprintf` 成功分配出参后 `free(out)`：不应报泄漏；测试应区分成功和失败路径。
- 对 `strstr` / `getenv` / `setlocale` 的返回值直接调用 `free`，不得被模型认定为正确、必要的释放行为。

### 9.2 Null-Deref

- `xmlReadMemory`、`xmlXPathNewContext`、`xmlXPathEvalExpression`、`cJSON_Parse`、`cJSON_GetObjectItem` 等返回值在未判空情况下被解引用：应被检测器按现有能力识别。
- 相同调用的返回值在解引用前经 `if (p == NULL) return/error;` 保护：不应报告。
- 在 `if (p != NULL)` 分支内解引用：不应报告。
- `xmlDocGetRootElement`、`xmlFirstElementChild`、`xmlNextElementSibling` 返回空的合法场景：仅在存在危险使用且缺少保护时报告。
- `strstr` / `strchr` / `strrchr` 未找到匹配项时返回 `NULL`，其结果未判空就解引用：应能检测。
- `getenv` / `setlocale` 返回值未判空就被危险使用：应能检测。
- 返回值只用于 `== NULL` / `!= NULL` 比较、没有危险解引用：不得报告 Null-Deref。
- 返回值被安全的早退、断言或现有规则认可的判空宏保护：不得误报。

### 9.3 所有权与别名

- `xmlDocGetRootElement(doc)` 返回的是文档树中的借用指针，不能被当作独立分配对象。
- 从 `cJSON_GetObjectItem` / `cJSON_GetArrayItem` 取得的 item 不能被当作新分配对象，也不应被默认单独 `cJSON_Delete`。
- `strstr` / `strchr` / `strrchr` 的结果是输入字符串内部指针，不应作为新分配对象。
- `cJSON_AddItemReferenceToObject/Array` 与拥有型添加函数必须有不同测试。
- `xmlDocSetRootElement` 替换旧根节点的情形应测试返回值/旧根节点处理；若当前分析器无法完全推理，应保证不输出确定但错误的结论。
- `xmlAddChild` / `xmlAddSibling` 的返回值和特殊节点处理至少有保守边界测试。

## 10. 验收标准

只有同时满足以下条件，才算完成：

- [ ] 第三方 API 语义可被独立维护，且没有散落在多个 detector 中的重复硬编码清单。
- [ ] 第一批清单中的函数均有明确的语义分类；不确定或有版本差异的 API 被显式标记，而不是伪装成确定规则。
- [ ] 分配、释放、所有权转移、返回值可空性、借用/别名语义相互独立。
- [ ] `asprintf` / `vasprintf` 的 `char **` 出参分配和成功条件得到正确建模。
- [ ] cJSON 拥有型添加与引用型添加不会被混淆。
- [ ] libxml2 文档、节点、XPath context、XPath object 不会互相错配释放函数。
- [ ] Null-Deref 只有在存在危险使用且缺少有效保护时才报告。
- [ ] 上述测试矩阵已落实到自动化测试，且相关测试通过。

- [ ] 文档说明如何增补 API 模型、如何验证官方语义和如何处理版本差异。

## 11. 不在本任务范围内

除非仓库现有架构要求且实施前能证明必要，否则不要顺带进行以下扩张：

- 不重写整个 SAST/SGRE 架构；
- 不引入新的大型指针分析或全程序分析框架；
- 不把所有未知外部函数都交给 AI 或一律当作 allocator；
- 不因某函数返回指针就默认其返回值需要释放；
- 不因某函数名含 `Add` / `Set` 就默认发生所有权转移；
- 不将库函数语义硬编码进每个 detector；
- 不为追求扫描数量而降低“确认”结果的证据标准。
