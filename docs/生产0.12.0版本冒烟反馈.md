# SecGuard 扫描问题与性能改进建议

> 基于一次真实全量扫描会话的观测记录，用于向 `secguard-clang` 提 issue。
>
> **本文档不依赖被扫描工程的源码**：检测器类问题配有**最小合成复现代码**（§附录 A）。
> 每个用例都标注了**实测复现状态**——8 个已在本机复现成功；5 个因触发条件依赖
> 工程规模或跨文件上下文，最小单文件用例未能构造，已改为引用真实候选的
> Hint + Code Context 原文（附在对应小节内），不臆造无法验证的用例。
> CLI 类问题用任意工程 + 文中给出的命令即可复现。

| 项目 | 值 |
|---|---|
| 工具版本 | `secguard-clang v0.12.0` |
| 宿主 | CodeAgentCLI（claude-cac） |
| 规模 | 341 文件 / 1713 函数 / 56447 行 |
| 候选 | 11256 seeds → 457 candidates（11 个类型有候选） |

| 扫描目录 | `.codeagent/secguard-clang/scans/<scan_id>/` |

## 零、复现指南（厂商视角）

本文档的问题分两类，复现成本都很低：

| 类别 | 复现方式 | 需要被扫描工程源码吗 |
|---|---|---|
| **A 类（CLI / 报告 / 状态机）** | 任意 C 工程跑一次 `secguard scan`，再执行文中命令 | 不需要 |
| **B 类（检测器误报）** | 把 §附录 A 的对应片段单独存成一个 `.c` 文件，跑 `secguard scan <file>` | 不需要 |

**建议的最小复现工程**

```bash
mkdir sg-repro && cd sg-repro
cp <附录A的片段> repro_a3.c        # 每个用例单独一个文件，避免互相干扰
secguard scan ./repro_a3.c
# 观察 candidates/<type>/_index.md 与 findings/ 是否出现该条
```

附录 A 末尾有**复现状态汇总表**，列出每个用例的「期望候选数 / 实测候选数」，
可直接作为回归用例。注意：**每个用例必须单独一个文件扫描**——
把多个用例放进同一文件会改变边界扫描的 fail-open 判定，导致结果与文档不符。

## 二、正确性问题（建议提 bug issue）

### A1. `report --audit` 无条件覆盖 `ai-dismissed.json`，清空驳回台账

**现象**

编排器按 skill 要求把 457 条驳回台账写入 `<scan_dir>/ai-dismissed.json`，随后执行最终 `report --audit`，该文件被重写为：

```json
{
  "dismissed": [],
  "scan_id": "sc_...",
  "total_dismissed": 0
}
```

**复现**

```bash
# 1. 写入台账
echo '{"scan_id":"x","total_dismissed":457,"types":[{"type":"null-deref","dismissed":230}]}' \
  > <scan_dir>/ai-dismissed.json

# 2. 跑审计
secguard report --audit --scan-id <scan_id> --output-dir <scan_dir>

# 3. 台账被清空
cat <scan_dir>/ai-dismissed.json
# => {"dismissed": [], "scan_id": "...", "total_dismissed": 0}
```

**影响**

- skill 明确要求「被驳回 / 未判定的候选绝不能只存在于子代理的聊天消息里」，而工具自己的审计步骤会把它抹掉。
- 文件名冲突：skill 指定的台账路径与工具内部生成的摘要文件**同名**，二者语义完全不同（一个是 AI 驳回明细，一个是工具统计）。

**建议**

1. 审计步骤改为**合并**而非覆盖；或
2. 工具改用不同文件名（如 `pipeline-dismissed.json`），把 `ai-dismissed.json` 留给编排器；或
3. 至少在覆盖前检测到非空内容时打印警告。

### A2. `report --list` 忽略 `--scan-id`，且输出形状随结果是否为空而变

**现象 1：`--scan-id` 无效**

```bash
secguard report --list --scan-id sc_DOES_NOT_EXIST --db <db>
# => 仍返回本次扫描的 2 条 finding（应为空）
```

**现象 2：输出形状不一致**

```bash
# 有结果 → 裸数组
secguard report --list --status dismissed --db <db>
# => [ { "id": 1, ... }, { "id": 2, ... } ]

# 无结果 → 对象
secguard report --list --status confirmed --db <db>
# => { "count": 0, "findings": [], "message": "no findings in database; ..." }
```

**影响**

- 任何 `jq '.[]'` 或 `json.load(...)['count']` 脚本都会在其中一种情况下崩溃（本次编排中实际触发过 `AttributeError: 'list' object has no attribute 'get'`）。
- 多扫描共用一个 DB 时，`--list` 会把历史扫描的 finding 一并返回，无法按扫描隔离。

**建议**

1. `--list` 支持并按 `--scan-id` 过滤；
2. 统一输出形状（恒为 `{"count":N,"findings":[...]}`，或恒为数组 + 空数组）。

### A3. `status --per-type` 的 `remaining` / `dismissed_count` 语义错误

**现象**

全部 11 个有候选的类型均已 `terminal_state=done`、`ai_stage_status=done`、`already_covered_ranges=['all']`，但：

```
divide-by-zero         cand=   1 written=0 dismissed=0 remaining=1  state=done
null-deref             cand= 230 written=0 dismissed=0 remaining=230 state=done
uninit                 cand=  82 written=0 dismissed=0 remaining=82  state=done
```

**影响**

- skill 的 F1 失败降级逻辑要求「`candidate_count > 0 && written_count == 0` 且未标 missing-type 时不得 audit」。若编排器同时参考 `remaining`，会把**已全部驳回**的类型误判为「未处理」，导致重复派发整个类型。
- `dismissed_count` 恒为 0，与「457 条已驳回」的事实矛盾。

**建议**

- `terminal_state=done` 时 `remaining` 应为 0；
- `dismissed_count` 应反映 `candidate_count - written_count`（在 done 状态下），或改名为 `persisted_dismissed_count` 并在 `--help` 中说明「dismissed 不落库，故恒为 0」。

### A4. seed → final → dropped 账不平

**现象**

`11256 (seeds) ≠ 457 (final) + 10353 (dropped)`，差额 **446** 条无任何解释。

| 类型 | seed | final | dropped | final+dropped | 差额 |
|---|---:|---:|---:|---:|---:|
| null-deref | 10793 | 230 | 10160 | 10390 | **403** |
| uninit | 164 | 82 | 50 | 132 | **32** |
| use-after-free | 20 | 5 | 7 | 12 | **8** |
| format-string | 5 | 2 | 2 | 4 | 1（auto-confirmed） |
| integer-overflow | 9 | 7 | 1 | 8 | 1（auto-confirmed） |
| stack-address-escape | 28 | 27 | 0 | 27 | 1（auto-confirmed） |
| 其余 5 类 | — | — | — | — | 0 |

两类缺口：

1. **auto-confirmed 条目不在任何计数里**：`final_count` 不含、`dropped` 不含，`audit-report.md` 的 `Auto-confirmed` 列也是 0（见 A5）。
2. **446 条既非 final 也非 dropped**：候选文件中可见「一个候选覆盖多个 sink」的说明（如 `This one candidate covers every dereference of X; ... line(s) 141, 142, 143`），**推测**为去重/合并，但日志中**没有任何 dedup/merge 记录**。

**建议**

- 在 `dismissed.json` 中增加 `merged` 原因桶，或在 `audit-report.md` 增加「Merged」列，使 `seed = final + auto + dropped + merged` 恒成立；
- `secguard metrics` 输出中补一个 `accounting_ok: true/false` 字段。

### A5. `auto_confirmed` 在 audit 报告层恒为 0，溯源信息丢失

**现象**

- `secguard scan` 摘要明确报告 `Auto-confirmed (pipeline-proved) | 2`；
- DB 中两条 finding 的 `status='auto-confirmed'` 仍在；
- 但 `report --audit` 的 `summary.auto_confirmed = 0`，`audit-report.md` 的 `Auto-confirmed` 列全为 0，`report.md` 的 "Findings by Skill" 表**只剩 TOTAL 行**（所有类型行消失）。

**影响**

- 无法从最终报告判断「哪些发现是机器判定的、哪些是 AI 判定的」——这正是交付时最需要审计的信息。
- 终审复核驳回后 `auto_confirmed` 归 0 可以理解（`EffectiveStatus` 生效），但报告应至少区分「机器判定后被驳回 N 条」，而不是让整张表变空。

**建议**

- `audit-report.md` 增加 `Auto-confirmed (reviewed-out)` 列；
- `report.md` 的 "Findings by Skill" 表保留所有有候选的类型行，而不是在 0 confirmed 时只留 TOTAL。

### A6. `report --list-auto-confirmed` 恒返回 0，命令实际不可用

**现象**

```bash
secguard report --list-auto-confirmed --db <db>
# => {"count": 0, "findings": []}
```

但 DB 中确实存在 2 条 `status='auto-confirmed'` 的行。

**根因（可从数据推断）**

auto-confirmed 行在写入时 `review_status='confirmed'`（机器判定即视为已复核），而 `--list-auto-confirmed` 的过滤条件是「无 review verdict」，两者互斥，故恒为空。

**建议**

- 修正过滤条件，或在 `--help` 中标注 DEPRECATED 并指向 `--list --status`。

### A7. 零候选类型需逐个 `--complete-type` 才置 done

**现象**

29 个类型中 18 个候选数为 0，其中 17 个在扫描结束后 `ai_stage_status` 仍为 `pending`。编排器必须对每个零候选类型调用一次 `report --complete-type`，否则 `audit-report.md` 中出现 17 行 `ai_stage_status=pending` 噪音。

**建议**

- 扫描结束时，`candidate_count == 0` 的类型自动置 `ai_stage_status='done'`；
- 或在 `audit-report.md` 中对零候选类型显示 `n/a` 而非 `pending`。

同一 subagent 因重试/补充写入了多个报告文件，`status --reports` 将它们全部列出：

report count: 22（实际批次只有 9 个）

**现象**

### A11. 两条确定性误报被 auto-confirm 直接进 SARIF

**现象（本次实测复现）**

附录 A 的两个最小用例，代码本身**完全无缺陷**，但都被流水线 auto-confirm，
即**不经 AI 研判直接进 `result.sarif`**：

| 用例 | 代码形态 | 实测结果 |
|---|---|---|
| §A-4 | `const unsigned char *h = haystack; return &h[i];` | `CWE-562, status=auto-confirmed, variable=h` |
| §A-10 | 同一 `va_list` 两次 `va_start` | `CWE-457, status=auto-confirmed, variable=args`（2 条） |

复现命令：

```bash
# 用例 1
cat > repro_a4.c <<'EOF'
const void *memmem_(const void *haystack, unsigned len,
                    const void *needle, unsigned nlen)
{
    if (!haystack || !needle || !nlen || nlen > len) return 0;
    const unsigned char *h = (const unsigned char *)haystack;
    const unsigned char *n = (const unsigned char *)needle;
    for (unsigned i = 0; i + nlen <= len; i++) {
        if (h[i] == n[0]) return &h[i];
    }
    return 0;
}
EOF
secguard scan ./repro_a4.c
# => Auto-confirmed (pipeline-proved) | 1
# => DB: rule_id=CWE-562, status=auto-confirmed
```

**为什么严重**

- auto-confirmed 的语义是「机器已证明，无需复核」，会直接写入 `result.sarif` / `result.xlsx`；
- 本次真实工程中，正是这 2 条 auto-confirmed 需要人工逐条复核才能驳回
  （`mgcp_common.c:186` 的 `&h[i]`、`dfx_debug.c:119` 的宏包装 format-string）；
- 若使用者信任 auto-confirm 而不做终审，这两条会作为**假阳性缺陷**进入交付物。

**根因（两处，均可定位）**

1. **`&h[i]` 被当作栈地址逃逸**：证明里出现 `object@h` + `escape-kind@return`，
   但 `decl@N` 那一行的 `h` 类型是**指针**，`&h[i]` 等价于 `h + i`，指向调用方缓冲区。
   检测器只看了「取址 + 返回」，没看被取址对象的**存储类**。
2. **`va_start` 宏写入未被识别**：`certain-uninit` 的前提是「该标量从未被写过」，
   而 `va_start` 是宏、CFG 不展开。单次 `va_start` 不触发，
   **两次 `va_start`** 时第二次的写入路径未被建模，导致误判。

**建议**

1. auto-confirm 前增加**前提校验**：
   - stack-address-escape：若 `decl@N` 的变量是指针类型，`&p[i]` 不构成逃逸，不得 auto-confirm；
   - uninit：`va_start` / `va_end` / `va_copy` 加入宏写入白名单，同一变量多次 `va_start` 均视为有效写入。
2. 对 auto-confirmed 提供 `--list-auto-confirmed` 的**可用**清单（见 A6），
   让使用者能逐条复核——当前该命令恒返回 0，等于没有复核入口。
3. 在 `report.md` 中显式标注「N 条 auto-confirmed 未经 AI 复核，建议人工确认」。

## 三、性能与成本问题（建议提 enhancement issue）

### B1. 索引图例重复，占索引体积 43%

**实测**

| 文件 | 总字节 | 数据行字节 | 图例字节 | 图例占比 |
|---|---:|---:|---:|---:|
| 全部 13 个 `_index*.md` | 236,910 | 134,910 | 102,000 | **43%** |

null-deref 分片时图例被**复制 3 份**：

| 文件 | 总字节 | 数据行 | 图例 |
|---|---:|---:|---:|
| `_index.md`（目录页） | 26,913 | 70（仅 2 行） | 26,843 |
| `_index_1.md`（#1–215） | 89,742 | 63,242 | 26,500 |
| `_index_2.md`（#216–230） | 30,808 | 4,308 | 26,500 |

即：**目录页 99.7% 是图例，且只有 2 行数据**；shard2 的 15 行数据被 26.5 KB 图例包裹，有效载荷比仅 14%。

**产物结构示意**（与具体工程无关，任何工程分片后都是这个形状）：

```markdown
# <type> (CWE-xxx) — Candidates

> Classify each candidate as confirmed / dismissed (BINARY).
> ...（分类说明 3 行）
>
> - `src@N` — the null/taint source is assigned at line `100` | `1007` | `101` | `102` | ...
>   ↑ 这一行把本次扫描所有出现过的行号平铺，实测单行 927 字节
> - `macro-context` — ...（约 200 字节）
> - `macro@<name>` — ...（约 250 字节）
> - `chain-root@<fn>` — ...（约 400 字节，列出所有 chain root）
> - `sibling-callers@<fn1,fn2>` — ...（约 1200 字节，列出所有 sibling 组合）
> - `callee@<file>:<line>` — ...（约 500 字节）
> - `null@cfg-proof` — ...（约 300 字节）
> - `null@malloc-fail` — ...（约 300 字节）
> - `null@caller-arg` — ...（约 200 字节）
> - `caller-null@<why>` — ...（约 300 字节）
> - `null@callback-entry` — ...（约 300 字节）
> - `null@opaque-origin` — ...（约 250 字节）
> - `null@assumed-return` — ...（约 300 字节）
> - `null@external-unknown` — ...（约 300 字节）
> - `guard@none` — ...（约 300 字节）
>
> Open the `Evidence` file ...（说明 3 行）

| # | Function | File:Line | Variable | Suspicion | Hint | Source | Evidence |
|---|----------|-----------|----------|-----------|------|--------|----------|
| 1 | ... | ... | ... | ... | ... | ... | ... |
```

图例部分约 26.5 KB，数据行每条约 295 字节。

**影响**

- 每个研判子代理都要读一次图例（~26 KB ≈ 7k tokens），11 个类型 × 多次分批 = 数十万 token 的纯重复开销；
- 分片本意是控制单文件体积，但图例复制使 shard2 的「有效载荷比」降到 14%。

**建议**

1. 图例抽到独立的 `candidates/LEGEND.md`（或 `_legend.md`），索引/分片只保留一行指针；
2. `src@N` / `chain-root@` / `sibling-callers@` 这类**枚举型**图例行改为固定说明 + 「见候选行」，不把本次扫描的实际值平铺进去；
3. 目录页只保留分片表，不复制图例。

### B2. 候选文件内嵌图例 + 泛化 Fix Suggestion，占 36%

**实测（457 个候选文件，共 2,026,297 字节）**

| 段 | 字节 | 占比 |

### B3. 分片严重失衡（93% : 7%）

**实测**

### B5. 上下文窗口不对称且截断 sink 后文

**实测**

457 个候选文件的 `## Code Context` 窗口：

| (sink 前, sink 后) | 条数 |
|---|---:|
| (8, 8) | 207 |
| (3, 3) | 55 |
| (12, 3) | 5 |
| (33, 3) | 3 |
| (16, 3) | 2 |
| 其他 | 185 |

窗口起点可近似反推为 `start = min(src_line - 3, sink - 8)`（114 条可验证样本中 104 条吻合），但**终点规则不统一**：389 条为 `sink + 8`，55 条只有 `sink + 3`，无法从数据反推出统一公式。

**问题 1：窗口严重不对称**

当 `src_line` 远早于 sink 时，起点被拉到 sink 之前几十行，终点却仍只有 sink+8（或 +3）：

| 候选 | 窗口 | sink | src | sink 前 | sink 后 |
|---|---|---:|---:|---:|---:|
| `001` | 99–144 | 141 | 102 | **42 行** | 3 行 |
| `016` | 291–327 | 324 | 294 | **33 行** | 3 行 |
| `011` | 167–182 | 179 | 170 | 12 行 | 3 行 |
| `002` | 301–317 | 309 | 303 | 8 行 | 8 行 |

**问题 2：窗口终点早于函数结束，收尾逻辑不可见**

`001` 的窗口 99–144，而该函数到 148 行才结束——145–148 的 `return HPE_OK;` 等收尾语句不在窗口内。

**窗口计算示意**（结构示意，非可复现用例——见 §附录 A-2 的说明）：

```c
int f(void *p) {              /* 行 95：函数起点 */
    ...
    if (p == NULL) return -1; /* 行 102：src@102 */
    ...
    x = p->field;             /* 行 141：sink */
    y = p->other;             /* 行 142 */
    p->f3 = 0;                /* 行 143 */
    cleanup();                /* 行 145 ← 不在窗口内 */
    return 0;                 /* 行 148 ← 不在窗口内 */
}
```

窗口 = `min(102-3, 141-8)` = 99 到 `141+3` = 144。

> 注：把这段代码单独存成文件扫描时，检测器能识别 `if (p == NULL) return` 已守卫，
> 不产生候选，因而**无法观察窗口**。上表的窗口数据全部取自真实工程的 457 个候选文件。

**影响**

- 研判子代理在需要「sink 之后是否有 guard / 是否有 free / 函数是否提前返回」时必须额外读源，直接消耗有限的 ≤5 次 source-read 预算；
- 本次 `uninit` 42–82 段 source_reads=15、`memory-leak` source_reads=12，均超出 ≤5 预算。

**建议**

- 窗口改为以 sink 为中心对称展开（至少 `sink ± 8`），并保证覆盖 sink 所在函数的首尾；
- 若因函数边界截断，在窗口头部注明「窗口已在函数边界截断」，让研判方知道需要补读。

**一个值得注意的附带发现**：A-9 的用例（`z1.c`）除了误报 use-after-free，
还在**同一份完全正确的代码**上误报了 memory-leak 和 integer-overflow：

```c
void parse(const char *buf, unsigned len)
{
    const char *cur = buf;
    while (cur < buf + len) {
        char *line = malloc(len + 1);   /* ← memory-leak 误报 */
        if (!line) break;
        use(line);
        free(line);
        cur += 1;                        /* ← integer-overflow 误报 */
    }
}
```

这说明「循环内 malloc/free + 指针递增」这一常见写法会同时触发多个检测器的误报，
建议作为一组回归用例。
