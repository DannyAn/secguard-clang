## 3. 四类举证不足根因（逐类回源验证）

### 3.1 unchecked-return —— 证据明文指令"去读定义体"（12 次读源，四类最大头）

**断链点 1：候选的 callee 定义体不嵌入证据。**
以 `allocator.c:114`（候选 001）为例，Hint 为 `contract@unknown callee@allocator.c:17 api@alloc_entry cat@unchecked_return`。证据文件内容：

- `Code Context` 只有**调用点 ±8 窗口**（main 函数内的调用行），不含 callee 定义体；
- `Contract` 行明文："You must prove the callee returns a failure sentinel … otherwise **dismiss**"；
- `Callee definition` 行只给**位置指针**（`allocator.c:17 (signature: alloc_entry(size_t size))`）与指令："**read the definition to prove or refute** that it returns a failure sentinel"。

根因定位：`sgre/internal/planner/registry.go:904-915` —— BuildEvidence 对 `contract@unknown` 且扫描内有定义的 callee，只生成位置 + 签名的 `callee_definition` fragment，并附带 "read the definition" 指令；`sgre/internal/report/markdown.go` 的 `candidateContext`（±8 窗口）与 `sourceSinkSpan`（markdown.go:402）均不感知 `CalleeDefLine`，跨文件 callee 永远不进 Code Context。

**结果**：AI 被证据文件明确指示去读 `allocator.c:17`。而该定义体（allocator.c:17-30，三条失败路径 `return NULL`）一旦嵌入，"confirmed" 从行内即可判定，读源完全可免。三个 allocator 候选全部 confirmed（结论正确），但每个都付出了读源成本。

**断链点 2：auto-confirmed 复核链路的 snippet 只有单行。**
29 条 auto-confirmed 复核走 `secguard review --list-auto-confirmed`，返回的 snippet 是**单行** `SourceLineText`（`sgre/internal/cli/report.go:323`），无 ±8 上下文。复核驳回 4 条（`fopen` 结果经 `return f != 0` 检查 ×3、`read()` 缓冲区从未使用）的判断都需要看语句周边——单行 snippet 撑不起，只能读源。**此缺口影响全部 22 个类型的复核链路**（本轮 117 条 auto-confirmed 复核），不止 unchecked-return。

**判据层附带问题（UC-04 FN，详见第 5 章）**：p13_v074_fp_fixes.c:191 的 `idm_new_idmgr(1)` 候选被 dismissed，理由"外部工厂、扫描内无定义体、结果以 `(void)p` 丢弃"——这是**事实正确**的（该函数仅有声明无定义），dismissed 是忠实执行 skill 判据的结果。

### 3.2 sizeof-misuse —— Hint 零语义事实 + skill 判据与 ground truth 直接冲突（P6-07 FN）

**断链点：Hint 与 Evidence 均无判据事实。**
唯一候选 `p6_new_detectors.c:67`（`char **p = malloc(n * sizeof(p));`）的 Hint 仅有 `cat@sizeof_pointer_ambig`。根因：`sgre/internal/planner/evidence_package.go:153-261` 的 `buildHint` switch **没有 sizeof-misuse 分支**（现有分支仅 unchecked-return / divide-by-zero / uninit / integer-overflow / deadlock / use-after-free / double-free）；BuildEvidence（registry.go:958-963）也只有两条通用 fragment（sink 文案 + call_path），**无指针层级（T\*\*）、无分配语义（数组 vs 单对象）、无元素类型**。

registry.go:950-957 注释明确了设计意图：`T **p` 的 `sizeof(p)` 可能是合法的指针数组分配，故意留 `suspected` 给 AI 裁决——**但没有给 AI 任何裁决所需的事实**。

**深层根因（判据层）**：AI 以"合法数组指针分配"为由 dismissed，而 ground truth P6-07 期望 finding。对照 skill 原文，AI 的裁决**正是 skill 教的**：

> `extension/shared/skills/sizeof-misuse/SKILL.md:33`：sizeof_pointer_ambig（char **p; malloc(n * sizeof(p))）→ **dismissed** — reason about the actual intent
> `SKILL.md:39`：sizeof(char*) used intentionally (array of pointers) → FP 模式
> `SKILL.md:52`：sizeof_pointer_ambig（pointer-to-pointer / pointer typedef）→ MEDIUM (**dismissed**)

**即：skill 判据与 benchmark 判据（P6-07 期望 finding、P6-08 `sizeof(*p)` 期望 no_finding）系统性冲突。证据不足只影响读源成本；判据冲突才导致 FN——即使证据充分，按 skill 判据 AI 依然会 dismiss P6-07。**

### 3.3 race-condition —— 事实已算出但不进 Hint（3/3 候选全部要开 Evidence）

**断链点：BuildEvidence 与 buildHint 之间的事实断层。**
BuildEvidence（registry.go:681-726）已经算出了研判所需的**全部关键事实**并写入 Evidence fragment：

- `shared_data_race`：ThreadFunctions（哪些线程函数访问）、ThreadInstances（线程实例数）、WriteLine（冲突写行号）；
- `toctou_shared_state`：Mutex 名 + LockLine/UnlockLine（锁区间）；
- `toctou`：CheckFunction → UseFunction（检查/使用调用对）、CheckPathArg（同一参数检查后使用）。

但 `buildHint`（evidence_package.go:153-261）**没有 race-condition 分支**，这些事实一个都不进 `_index.md` 的 Hint 列——AI 只看到 `cat@toctou` 等通用 token，**每个候选都必须打开 Evidence 文件**才能研判（本轮 3 候选 → 3 次 evidence_open，100% 依赖率，另有 1 次读源）。

结果全部正确（3/3 confirmed），但这是四类中"事实已备、只差接线"的最典型案例——修复成本最低、收益最直接。

### 3.4 path-traversal —— 参数路径候选零 caller 事实 + skill 判据与 ground truth 直接冲突（P6-05 FN）

**断链点：tainted 候选有事实，参数路径候选没有。**
- tainted 候选（p10_interproc_taint.c:24/:39 等）：Hint 带 `src@N tainted`，Evidence 带 `taint_source` fragment——4 条全部正确 confirmed，无需读源。
- **参数路径候选**（p6_new_detectors.c:51、system.c:46）：无 caller 清单、无污点可达性事实。BuildEvidence（registry.go:927-939）只有通用 sink 文案 + `path_arg`，且仅在 `HasTaintSource` 时才有 `taint_source` fragment。

**深层根因（判据层）**：AI 以"unproven-taint 参数无 tainted caller"为由 dismissed p6:51（`tp_path_traversal(const char *path)` 内 `fopen(path, "r")`），而 ground truth P6-05 期望 finding（判据：**非字面量路径即 finding**，对照 P6-06 字面量路径 no_finding）。skill 原文：

> `extension/shared/skills/path-traversal/SKILL.md:32`：fopen(path, ...) where path is a function parameter with no provable tainted caller → **dismissed**
> `SKILL.md:35-37`：The **confirmed** verdict only applies when the pipeline proved a taint source … A parameter of unknown origin stays **dismissed** — do not promote it without tracing a caller

**同样是 skill 判据与 benchmark 判据的直接冲突**：benchmark 按"攻击面"报（非字面量路径暴露 CWE-22），skill 按"可证明污点"报（噪声控制）。system.c:59 `openat(...O_NOFOLLOW)` 的 dismissed 合理（有真实防御事实），p6:51 的 dismissed 是判据冲突产物。

## 4. 三层根因模型（总结）

四类问题不是同一个病，而是三层断链，每类症状由不同层主导：

| 层 | 问题 | 表现 | 受影响类型 |
|----|------|------|-----------|
| **证据层** | Hint/Evidence 缺关键事实，证据文件明文指令读源 | 反复读源、预算超标、evidence 依赖率 100% | unchecked-return（callee 体不嵌入）、race-condition（事实不进 Hint）、path-traversal（参数路径无 caller 事实）、sizeof-misuse（零语义事实）+ 全类型复核 snippet 单行 |
| **判据层** | skill 研判判据与 benchmark ground truth 冲突，AI 忠实执行 skill → 必然 FN | 3 条 FN（P6-05、P6-07、UC-04），全部集中在批次 C 四类范围 | path-traversal、sizeof-misuse、unchecked-return（外部 callee 分支） |
| **回归层** | 会话流程未跑 benchmark validator；validator 自身还有映射 bug | FN 只能靠人工对账发现；TP-02 被 validator 误报 FN | 全局 |

**关键定性**：证据层问题浪费 token（可量化：四类 16 读 + 11 开，全会话 44 读 + 21 开）；**判据层问题直接产生漏报**——且责任不在子任务 AI（其 dismissed 理由均可在 skill 原文找到逐字依据），在 skill 判据与 benchmark 的设计分歧未被闭环。

## 7. 改建建议（完整自洽方案）

按"先止血 FN、再降 token、后治理流程"排序。涉及 skill 的修改必须走 `ADDING_A_VULN_TYPE.md` 流程并过 `TestVulnTypeSkillConsistency` 守卫（改 `extension/shared/skills/`，不动生成副本）。

### P0-1 判据对齐：skill 判据向 benchmark 判据收敛（消除 3 条必然 FN）

三类冲突必须逐一定夺方向。**推荐统一以 benchmark 判据为准修改 skill**（benchmark 的 finding/no_finding 对照用例本身就是设计意图的声明：P6-05/P6-06、P6-07/P6-08、UC-03/UC-04 成对存在）：

1. **path-traversal SKILL.md**：判据改为"**可达文件系统 sink 的非字面量路径参数 = confirmed（CWE-22，confidence: medium）；流水线证实污点 = confidence: high**"。删除"parameter with no provable tainted caller → dismissed"与"do not promote without tracing a caller"条款。噪声风险评估：本轮流水线 taint 过滤仅弃 2 条、7 候选中仅 3 条参数路径受影响，且 confidence 分级保留降噪空间；生产大库如需更强降噪，可在证据中补 caller 清单后由 AI 升降级，而非一票否决。
2. **sizeof-misuse SKILL.md**：判据改为"**分配上下文中 sizeof 作用于指针变量 = confirmed（CWE-467 反模式，无论指针层级——`sizeof(p)` 依赖 p 自身类型，脆弱且非意图表达）；`sizeof(*p)` / `sizeof(元素类型)` = 安全**"。删除 sizeof_pointer_ambig → dismissed（:33、:52）与 "array of pointers 属合法意图"（:39）条款；P6-07/P6-08 成为回归对。
3. **unchecked-return SKILL.md**：外部分支判据改为"**`*_new`/`alloc` 名字启发式命中的外部工厂，其返回值被丢弃或未检查 = confirmed（confidence: medium）**；标准 API（malloc/fopen 等契约已知类）维持原判据"。删除"If you cannot prove it, dismiss"（:34）；UC-03/UC-04 成为回归对。

### P0-2 validator 修复 + 会话收尾自动对账

1. `CWE_TO_TYPE` 补 `"CWE-89": "injection"`；并以 `planner.AllCWEs()`（Go 侧唯一权威源）为参照审计映射表完整性，防止下一个缺失 CWE 再造假 FN。
2. 在 `command-instructions.md` 收尾阶段增加一步：**benchmark 项目（存在 `expected-results.json`）在 summary 前必须跑 `validate-benchmark.py` 并将 FN/FP 计数写入会话结论**——让 FN 在会话内闭环，而非依赖事后人工自检。

### P1 证据层增强（消除读源，预计消掉本轮 44 次读源的大半）

1. **buildHint 补三个分支**（`evidence_package.go:153`）：
   - race-condition：`mutex@<name>`、`lock@<N>-<N>`、`threads@<n>`、`check@<fn>→use@<fn>`、`arg@<expr>`——字段全部已在 Candidate 上（BuildEvidence 正在用），纯接线工作；
   - path-traversal：`path-kind@param|tainted`、`callers@<none|n>`；
   - sizeof-misuse：`ptr@<声明类型>`、`alloc@<分配表达式>`、`elem@<元素类型>`（若 detector 未持久化则需同步补 Candidate 字段）。
2. **unchecked-return 嵌入 callee 定义体**：`contract@unknown` 且 `CalleeDefFile` 非空时，Evidence 的 Code Context 追加 callee 定义体（截断上限如 30 行），并把 registry.go:910 的 "read the definition" 指令改为"定义体已嵌入上方，直接研判"；同文件 callee 可同时把 `CalleeDefLine` 纳入 `sourceSinkSpan`（markdown.go:402）窗口。本轮 allocator 三候选的 3+ 次读源即可归零。
3. **复核 snippet 加上下文**：`cli/report.go:323` 的单行 `SourceLineText` 换成与候选 Evidence 一致的 ±8 窗口（复用 markdown.go 窗口构造）。惠及全部 22 个类型 117 条复核，是单点收益最大的改动。
4. **path-traversal 补 caller 事实**：参数路径候选增加 caller 清单 fragment（扫描内调用点，或"no callers in scan"），让"参数来源不可知"从 AI 的猜测变成证据事实，配合 P0-1 判据做置信分级。

### P2 自报可信度治理

1. 回报 schema 拆分：`dismissed` → `candidates_dismissed` + `re_review_dismissed`（改 `command-instructions.md` 的 schema 定义处）。
